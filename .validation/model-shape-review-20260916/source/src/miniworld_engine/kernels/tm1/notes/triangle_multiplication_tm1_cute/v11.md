# triangle_multiplication_tm1_cute - optimization round v11 (persistent warp-specialized GEMM — CORRECT but SLOWER)

- Date: 2026-07-04
- Goal (roadmap 3): persistent + warp-specialized tcgen05 GEMM to break the 12% single-warpgroup occupancy wall and beat cuequiv (1.345ms).
- Baseline: v8 cute 1.560ms; tm1 gate_gemm ~0.316ms/side. Shipping unchanged (v8) — this regressed.

## 1. Built it (standalone, correct)
Wrote a full persistent, warp-specialized SM100 tcgen05 GEMM from scratch in 4.4.2 primitives
(the CUTLASS persistent reference is newer-cutlass; its harness/scalar-smem/3D-leading-dim APIs
are incompatible with 4.4.2, so I ported the STRUCTURE, not the file). Artifact: v11/persistent_gemm.py.
- Warp specialization: epilogue warps 0-3 (128t), MMA warp 4, TMA warp 5 (192 threads/CTA).
- StaticPersistentTileScheduler over M-tiles; PipelineTmaUmma (handle API) for AB, PipelineUmmaAsync
  (num_acc_stage=2) for the accumulator so epilogue(tile i) overlaps MMA(tile i+1).
- Direct register->gmem epilogue (per-tile make_tmem_copy, as the reference epilogue helper does).
- Correctness: plain C=A@B.T, M=1048576, N=K=128: **cos 0.999999** vs torch.

## 2. Measured: it is ~4x SLOWER than v8 (roadmap 3 fails)
do_bench (GPU0, mac cached): persistent **1.213 ms/side** vs gate_gemm **0.316 ms/side**.
ncu (single launch, cache-flushed): duration 2.07ms, grid **148 (=1 CTA/SM)**, waves 1,
sm__warps_active **9.3%**, dram 3%, sm 10%, **long-scoreboard stall = 121 inst/issue** (massive
memory-latency stalling).

## 3. Structural reason (definitive)
The persistent warp-specialized design is built for COMPUTE-bound large GEMMs, where few big
persistent CTAs + pipeline overlap hide load latency behind heavy MMAs. This tm1 GEMM is
MEMORY-LATENCY-bound: tiny N=128, huge M=1,048,576, reading x dominates (~1GB traffic), the MMA is
trivial. For such a workload, latency hiding needs MANY concurrent warps/CTAs:
- v8 (non-persistent): 8192 CTAs, 2 CTA/SM (smem), 12% occ — but the 8192 independent CTAs give
  strong CTA-level latency hiding (the HW scheduler interleaves them). -> 0.316ms/side.
- persistent: 148 CTAs, 1 CTA/SM (192KB smem from num_ab_stage=3 x 2 operands x 32KB), 6 warps/SM,
  9% occ — each CTA runs 55 tiles serially and 6 warps cannot hide DRAM latency (long_scoreboard 121).
  -> 1.213ms/side.
Persistence REDUCES the parallelism that was hiding latency. Reducing smem (smaller tile_k / fewer
stages) to raise CTA/SM was already shown (v9) to not help (tile_k=32 -> 4 CTA/SM ran slower), because
the wall is DRAM-latency at low occupancy, and this shape can't reach latency-hiding occupancy with
tcgen05's smem/tmem footprint.

## 4. Conclusion: all three roadmap items measured, none beat v8
1. ln fusion (v10): regressed (algebraic epilogue gather 0.843 vs 0.629; torch var_mean slow).
2. both-sides fuse (v9): regressed (4-acc -> 512 TMEM -> 1 CTA/SM).
3. persistent warp-specialized (v11): 4x slower (memory-bound, 1 CTA/SM, long-scoreboard stalls).
The tm1 GEMM is memory-latency-bound and v8's many-CTA non-persistent structure is near-optimal for
this shape. cuequiv (1.345ms) fuses the WHOLE trimul into few kernels avoiding the 5x 256MB
intermediates; matching it requires that whole-pipeline fusion, not a faster tm1 GEMM.
