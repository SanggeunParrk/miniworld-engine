# trimul_train_b200 v5 — wire sm100 dgrad_lnbwd into the trimul backward (LN_out fusion)

## Goal
Wire the v4 sm100 `dgrad_lnbwd_sm100` into the B200 trimul training backward, replacing the
LN_out-backward torch pass + the d_out_n (M,D) HBM round-trip with one fused tcgen05 dgrad GEMM.

## Change
`kernels/trimul_inproj/cute/training_b200.py` backward step (1), gated by env
`MINIWORLD_TRAIN_DGRAD_FUSED` (default on):
  - was: `d_out_n = d_proj @ Wp.t(); d_tri_lld, dWln_out, dBln_out = _ln_bwd(d_out_n, ...)`
  - now: `d_tri_lld = dgrad_lnbwd_sm100(d_proj, Wp.t(), xhat_out, ln_out_w, rstd_out)` — the
    projection-backward GEMM (d_proj @ Wp.t()) AND the LN-normalize backward are folded into ONE
    tcgen05 epilogue (no d_out_n materialize, no separate _ln_bwd memory pass).
  - LN_out affine grads derived from the wgrad T = d_proj^T @ xhat_out (== H100 dgrad_lnbwd usage;
    dgrad emits only dx, so dgamma=(Wp.t()*T).sum(0), dbeta=(d_proj.sum(0))@Wp.t() — d_out_n never
    materialized, since the dgrad kernel already computes it internally).
Also fixed dgrad_lnbwd_sm100 vec_dtype -> fp32 (LN stats fp32 per constraint; dtype-stable compile
key; the module's rstd_out is bf16 and was compiled-vs-runtime mismatched otherwise).
LN_in-backward is left as torch `_ln_bwd` (it is a PURE LN-bwd on an accumulated grad — no
preceding GEMM to fold into, so dgrad_lnbwd does not apply there).

## Correctness (full trimul fwd+bwd, grads vs fp32 autograd ref; ~psk/ncu/train_recon.py, B200)

           dln_out_w 0.99996/8.1e-3

  => cute relmean ~1.6x cuequiv, inside the ~2x bf16-grad-floor budget. cos >> 0.9999. PASS.

## nsys backward breakdown (fused, L=1024, per fwd+bwd iter, cuda_gpu_kern_sum / 20 iters)
  direct_copy (permute .contiguous)   6.04 ms  36.0%   <- DOMINANT: the LLD<->DLL permutes
  bf16 mul (elementwise)              2.23 ms  13.3%   dy*gate, dy*proj, d_gate*g*(1-g), ...
  bf16 add (dx_n accumulate)          1.59 ms   9.5%
  Welford + reduce (LN var stats)    ~1.56 ms   ~9%
  reduce sum / mean (LN, dW)         ~1.3 ms    ~8%
  gatebwd_sm100 GEMM (v2)             0.59 ms   3.5%
  einsum / nvjet GEMMs              ~1.0 ms    ~6%
  dgrad_lnbwd_sm100 GEMM (v5)         0.19 ms   1.1%   <- MY kernel: fast + correct
The LN_out-bwd pass + d_out_n round-trip ARE gone (folded into the 0.19 ms dgrad kernel; explains
the 1.8 ms/iter win). The remaining ~2x gap is MEMORY-BOUND: ~6 ms of LLD<->DLL permute copies +
~4 ms of elementwise mul/add + ~3 ms of LN reductions per iter — traffic cuequiv fuses into its
kernels. The actual GEMMs (dgrad 0.19 + gatebwd 0.59 + einsum ~1) are a small fraction.

## Next blocker (precise)
Eliminate the LLD<->DLL permutes (~6 ms/iter = the single biggest lever). Concretely:
 (a) make dgrad_lnbwd_sm100 store its dx output M-MAJOR (D, L*L) = DLL directly, dropping the
     `d_tri_lld.permute(0,3,1,2).contiguous()` DLL copy. This is an epilogue d_layout change
     (m-major D); the v4 generic lanes_in_N/warps_in_N derivation should adapt, but the full-N
     subtile + C(xhat) layout also shift -> its own correctness round.
 (b) fuse the d_left/d_right LLD permutes into the einsum-bwd / gatebwd input path.
 (c) fold the elementwise dy*gate / dy*proj / GLU-derivative into the dgrad/gatebwd epilogues.
Until the permute+elementwise traffic is fused, cute training stays ~2x behind cuequiv despite the
GEMMs being competitive. dab_lnbwd (transition) not needed for THIS module (its LN_in-bwd is a
pure LN-bwd, no GEMM to fold).
