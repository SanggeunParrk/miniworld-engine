# triangle_multiplication_tm1_cute - optimization round v9 (SM100 GEMM optimization exploration + diagnosis)

- Date: 2026-07-04
- Goal: make the SM100 tm1 GEMM fast enough that the cute path beats cuequiv (< 1.345 ms @ L=1024).
- Baseline: v8 cute 1.560 ms (cuequiv 1.345, quack-v2 1.506). Shipping unchanged (v8) — no experiment beat it.

## 1. Experiments (all correctness cos 0.999999 vs torch; do_bench GPU0 arbiter)
Artifacts: `v9/micro_fused.py` (both-sides fuse), `v9/micro_gate2.py` (K-looped), `v9/ncu_gk_occupancy.txt`.

a) **Fuse both sides into one launch, 4 TMEM accumulators (proj_l,gate_l,proj_r,gate_r)** — REGRESSED.
   - Correct, but full L=1024 cute 1.990 ms (vs 1.560). 4 accumulators = 512 TMEM cols = **1 CTA/SM**
     (tmem-limited), halving occupancy. Reverted.
   - Bug found+fixed en route: reusing one TMA atom for all 4 weights reads only the first weight's
     address (atom bakes the tensor base ptr) -> use a distinct make_tiled_tma_atom_B per weight.

b) **`_THREADS=256` (2 warpgroups)** — BROKE correctness (cos 0.53): the epilogue tmem->reg tiled
   copy is warpgroup(128)-sized; extra warps corrupt it. Needs real warp specialization. Reverted.

c) **K-looped mainloop (tile_k<128, multi-stage AB pipeline)** — MARGINAL. Both-sides GEMM do_bench:
   tile_k=64 s2 0.621 ms, tile_k=128 s1 0.629 (=v8), tile_k=32 s2 0.640, tile_k=32 s4 0.637.
   ~1% at best; not worth a shipping change.

## 2. ncu diagnosis of the tm1 GateGemm (L=1024, GPU0)
| metric | value |
|--------|-------|
| sm__throughput | 32% |
| dram__throughput | 12% |
| gpu__compute_memory_throughput | 14% |
| **sm__warps_active (achieved occupancy)** | **12%** |
| occupancy limit: shared_mem | **2 blocks/SM** (binding) |
| occupancy limit: registers | 6 blocks/SM |
| registers/thread | 80 |
| waves/SM | 27.7 |

- The kernel is **latency/stall-bound at 12% occupancy**, NOT compute- or bandwidth-bound
  (dram 12%, sm 32%). Effective BW ~1.6 TB/s vs B200 ~8 TB/s peak → 5x headroom unused.
- Occupancy is **smem-limited to 2 CTA/SM**. But shrinking smem via smaller tile_k did NOT speed it
  up (tile_k=32 raised occupancy yet ran slower) → the wall is the **single-warpgroup structure**
  (one warp issues the MMA; one warpgroup does the epilogue), not tiling. The MMA-issue + serial
  epilogue don't expose enough parallelism regardless of CTA/SM.

## 3. Why the cute path can't beat cuequiv yet (the real bottleneck)
Per-forward nsys (L=1024): ln_in 185 + **tm1 632** + einsum 192 + ln_out 302 + tm2 253 = ~1564 us.
Each of the 5 stages round-trips a 256 MB intermediate (x_normed, left/right, tri_out, out_normed)
-> ~2.5 GB of intermediate traffic. The cute path is **intermediate-traffic + kernel-count bound**;
cuequiv fuses the whole trimul into far fewer kernels. Optimizing the tm1 GEMM alone (0.62 ms floor
with this structure) cannot get the total under 1.345 ms.

## 4. Roadmap to beat cuequiv (ranked, for v10+)
1. **Fuse ln_in into the tm1 GEMM** (normalize each A-tile row on load; tile_k=128=full D). Removes
   the 185 us ln_in kernel AND the x_normed intermediate. ~ -185 us -> ~1.375 ms.
2. **Fuse both sides reading x once** (sequential, 2 TMEM accumulators to keep 2 CTA/SM; load x once,
   load Wp/Wg per side reusing smem). ~ -150 us (one fewer x read). Combined with (1) -> ~1.22 ms < cuequiv.
3. Persistent + warp-specialized GEMM (dedicated load/MMA/epilogue warps, 2 warpgroups) to lift the
   12% occupancy — the structural fix for the tm1 GEMM itself.
4. Attack ln_out (302 us, 90% mem-io transpose) and tm2 (253 us).

## 5. Validation / shipping
Shipping remains v8 (`bdll_sm100` -> two `gate_gemm` launches). compare_cute cos 0.999977 (== triton).
No regression. do_bench GPU0: cute 1.560 ms, cuequiv 1.345 ms.
