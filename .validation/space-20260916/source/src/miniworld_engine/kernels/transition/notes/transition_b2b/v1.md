## v0 Evidence

- v0 kernel: hand CuTe fused b2b, LN + expand + gate + squeeze, two consumer warpgroups, TMA weight ring, `h` kept in registers.
- Runtime: `658 us` at `M=524288`, `0.825x` of Triton (`543 us`), cosine `1.0`.
- ncu at `M=262144`: SM `31%`, occupancy `12.5%`, IPC `1.0`.
- Stalls: wait `1.36`, lg throttle `1.40`, long scoreboard `0.79`, barrier `0.53`, GMMA `0.26`.
- Compute roofline estimate: about `200 us`, or `2.7x` headroom.
- Prior hand levers reached a coupled-stall plateau: bespoke ping-pong with a dedicated producer warpgroup and NamedBarrier ordering both regressed by trading one stall class for another.

## Bottleneck Theory

The v0 kernel is not limited by math throughput. The low SM utilization, low occupancy, nonzero GMMA stall, and paired wait/lg throttle indicate that weight movement, barrier timing, and math issue are not balanced. The current cooperative path issues TMA from one thread inside a `ProducerConsumer` pipeline object shared by the same CTA body that also performs the math. That keeps correctness simple, but it does not mirror CUTLASS's production SM90 warp-specialized structure: a load warpgroup with reduced register allocation feeds two math warpgroups through a `PipelineTmaAsync` producer/consumer contract, and consumers release stages only after the GMMA tail is known complete.

The v1 hypothesis is that adopting CUTLASS's real cooperative role split and pipeline ordering should reduce exposed GMMA idle without raising long scoreboard. Expected metric movement: GMMA stall approaches zero, long scoreboard remains near v0 or lower, SM% rises materially, and the end-to-end runtime can move below Triton's `543 us` if the extra producer warpgroup does not cap occupancy or add too much scheduling overhead.

## Plan

Focused experiment: keep the existing fused b2b math, but replace the hand-rolled `ProducerConsumer` weight-ring scheduling with CUTLASS's cooperative warp-specialized skeleton.

Mirrored CUTLASS structures:

- `cutlass/gemm/kernel/sm90_gemm_tma_warpspecialized_cooperative.hpp`: one producer/load warpgroup plus two consumer/math warpgroups; load WG uses `warpgroup_reg_dealloc`, math WGs use `warpgroup_reg_alloc`; producer calls the mainloop load path and then `load_tail`; consumers wait on the mainloop pipeline, run math, tail-wait, then release.
- `cutlass/gemm/collective/sm90_mma_tma_gmma_ss_warpspecialized.hpp`: `PipelineTmaAsync` acquire -> `producer_get_barrier` -> TMA copy -> advance producer state; consumer `try_wait`/`wait`, GMMA, `warpgroup_wait`, `consumer_release`.
- `cutlass/pipeline/sm90_pipeline.hpp`: `PipelineTmaAsync` role separation (`Producer` vs `Consumer`) and `producer_tail` to avoid producer early-exit while consumers still own stages.

This round does not instantiate a full CUTLASS `CollectiveBuilder` for the two-GEMM fusion. The implementation adopts CUTLASS's cooperative mainloop skeleton and barrier ordering, adapted around the existing fused expand/gate/squeeze math.

## Code Changes

- CTA shape changed from `2 x 128` threads to `3 x 128` threads:
  - WG0: dedicated TMA producer
  - WG1/WG2: two existing math consumers, each computing `64 x 128` output rows
- Added explicit constexpr knobs:
  - `kConsumerWarpgroups = 2`
  - `kProducerWarpgroups = 1`
  - `kPipelineStages = 2`
  - `kBn = 64`
  - `kLoadRegisterRequirement = 40`
  - `kMmaRegisterRequirement = 232`
- Added `cutlass/arch/reg_reconfig.h` and applied CUTLASS-style register reconfiguration:
  - producer WG: `warpgroup_reg_dealloc<40>()`
  - consumer WGs: `warpgroup_reg_alloc<232>()`
- Changed `PipelineTmaAsync` params from `ProducerConsumer` to role-specific:
  - WG0 gets `ThreadCategory::Producer`
  - WG1/WG2 get `ThreadCategory::Consumer`
  - `num_consumers = 256`
- Moved all TMA weight stages into the producer WG:
  - prefetch TMA descriptors
  - loop over all `ND` tiles
  - `producer_acquire`
  - issue `wa`, `wb`, `ws` TMA copies against the producer barrier
  - advance producer state
  - `producer_tail` before producer exit
- Consumer WGs now:
  - stage and normalize their private `x` tile
  - participate in a block sync before producer/consumer role divergence
  - use `consumer_try_wait` + `consumer_wait`
  - run expand `wa`, expand `wb`, SwiGLU, and RS squeeze WGMMA
  - `warpgroup_wait<0>()` and fence before `consumer_release`

## Bottleneck Verdict

The v1 hypothesis was only half-right. The CUTLASS-style cooperative role split reduced GMMA stall from `0.26` to `0.15`, so the dedicated producer did feed tensor cores more consistently. However, the structure paid for that improvement with a much larger synchronization and residency tax: barrier stall rose to `2.12`, LG throttle stayed high at `1.44`, long scoreboard rose to `1.10`, and the `384`-thread CTA with about `131 KB` shared memory stayed limited to `1 CTA/SM`.

The dedicated producer warpgroup is the wrong structure for this small-tile fused b2b. TMA needs one issuing thread, but v1 spends a full 128-thread warpgroup on production and forces the consumers through a shared-ring `consumer_wait`/`consumer_release` handshake. The net result is `752 us` (`0.717x` of Triton), worse than the v0 baseline's `658 us` (`0.825x`).

This matches the earlier hand-rolled 3-WG and ping-pong attempts: moving weight movement into a dedicated producer can reduce one visible tensor-core stall, but the barrier/occupancy cost outweighs it for this fused transition tile.

## Risks

- The extra producer warpgroup increases CTA threads from 256 to 384. With dynamic smem still about `131104` bytes, expected residency remains one CTA per SM; occupancy may stay low or regress if register redistribution is ineffective.
- The x-normalization prologue still uses consumer-side `cp.async` and a CTA sync before TMA production starts. This preserves correctness but means v1 is not a full CUTLASS collective conversion.
- `consumer_release` now happens after the squeeze GMMA tail wait on every ND chunk. This is faithful to CUTLASS buffer ownership but can expose barrier overhead if the b2b inner work is too small per stage.
- Correctness depends on the producer stage sequence matching `chunk % kPipelineStages` and consumers consuming the same sequence; H100 cosine validation is required before any performance conclusion.

## Revert Status

**REGRESSED - reverted.** The kernel code is restored to the v0 baseline: 2 consumer warpgroups, inline `tid0` TMA, no dedicated producer warpgroup, and no shared-ring producer/consumer handshake. The winning current structure remains v0 at `0.825x` of Triton.

## Next Ideas

- v2 candidate: instantiate CUTLASS's actual tested `CollectiveBuilder` GEMM scheduler instead of another hand-built warp-specialized skeleton. This is the only remaining structural lever that is meaningfully different from the failed hand-built cooperative/ping-pong variants.
- Caveat for v2: `transition_b2b` is a two-GEMM fusion (`gate` and `h` flow between GEMMs, with `h` not written to HBM). CUTLASS `CollectiveBuilder` does not support this fused b2b out of the box. A real v2 would require a CUTLASS b2b collective port: first GEMM epilogue fused directly into the second GEMM mainloop.
- Cheaper alternative: micro-tune the v0 baseline's remaining coupled stalls (`wait 1.36`, `lg_throttle 1.40`). This path has already resisted about five focused attempts, so expectations should be modest.
- Do not spend another round on a dedicated producer warpgroup plus shared-ring consumer handshake for this shape. The measured regression makes that structure a dead end unless the tile size or residency constraints change.
