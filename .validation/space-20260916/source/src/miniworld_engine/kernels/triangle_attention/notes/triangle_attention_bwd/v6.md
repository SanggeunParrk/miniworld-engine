# triangle_attention — v6: forward `out` in projection layout (kills the "B" fwd copy) — 1.72× vs baseline

**GPU:** H100 (sm90).  **Shape:** d_pair=512, L=384, n_head=4 → HEAD_DIM=128, B=1, bf16.
**Base:** v5 (strided dq/dk/dv writes + strided grad_output, 6.58 ms/layer).  **Baseline:** 10.98 ms.

## Verdict

**SHIP.** Symmetric to v5's A/C, applied to the **forward output**: write `out` directly into
the **projection layout** `[B,L,L2,H*D]` (strided `[B,H,L,L2,D]` view) so the module's
`rearrange(out, "B H L L2 D -> B L L2 (H D)")` (module.py:275) is a **FREE view** — kills the
~0.18 ms forward `[B,L,L2,H,D]` copy ("B"). Correct (cos 0.99999 / 0.99998), **step
6.58 → 6.403 ms (1.03× vs v5, 1.72× cumulative)**.

## The "B" copy

`attn_out` was a contiguous `[B,H,L,L2,D]`; merging the head back to `[.,H*D]` for the
gate/`to_out` path requires H,D adjacent+contiguous, which they are not (H is dim1, D is
dim4) — so `rearrange` permuted to `[B,L,L2,H,D]` then **materialized it contiguous** to flush
the merge: a `[1,384,384,4,128]` copy, ~0.2 ms/step. Not an explicit `.contiguous()` (einops-
internal → no Python stack, which is why the with_stack profiler couldn't pin it).

## Fix (main.py only — no module change)

- **Forward:** allocate `out_proj = empty(B,L,L,H*D)`; `out = rearrange(out_proj,
  "B L L2 (H D) -> B H L L2 D")` (strided view); pass `*out.stride()` as the o-group; the
  `_attn_fwd` epilogue writes strided (head_dim stride-1 → coalesced, free like q/k/v). Save &
  return the strided view — its storage IS `[B,L,L2,H*D]`, so the module's out-rearrange is a
  free view (no code change at module.py:275).
- **Backward preprocess:** `out` is now strided 5D; `_attn_bwd_preprocess` reads it via its own
  explicit strides (`os_*`, b/h/i_row decomposition) exactly like `do` (C). Pass `*out.stride()`.

## Validation

`ta_verify.py` D=512 L=384 NH=4 bf16 vs pytorch fp32 ref: fwd cos 0.99999, grad_pair cos
0.99998, PASS. Precision unchanged.

| version | step | vs baseline |

Forward copies after v6: only `bias.contiguous()` `[1,4,384,384]` (~0.0 ms, intentional — the
gappy pair-bias load is the whole stride penalty, cheap to copy). The `[1,384,384,4,128]`
forward copy is gone.

## Remaining (not B, lower priority)

- backward `copy_ [1,4,384,384,128]` ~0.13 ms/step — a separate backward-side materialization
  (likely the fp32 `dq_proj` grad path); orthogonal to B.
- backward `add_ [1,384,384,512]` ~0.5 ms/step — pair-grad accumulation (pair feeds 5
  projections), inherent autograd, not a copy.
- dbias per-row `[B,HL,L,L]` materialize + `reduce(sum)` — could fuse the row-reduction.
