# trimul_train_b200 v10 — eliminate physical _fast_T transposes via strided views (H100-bidir style)

## Goal
Remove the physical `_fast_T` LLD<->DLL transpose copies (~0.485 ms/iter = ~10% of bwd @L1024)
by feeding STRIDED VIEWS into the consumers, mirroring H100 `bidir_training.py`.

## Analysis of the 4 training transposes (which can be a strided view?)
The rule: a consumer accepts a strided view only if its needed dim stays CONTIGUOUS.
- **#1 fwd tri_lld (DLL->LLD), consumer = fused triton LN_out**: ELIMINATED. LN reads tri
  (DLL) via an M-major view `tri.reshape(D,M).t()`; the kernel takes input strides (sxm,sxd)
  and writes contiguous (M,D). m is contiguous in DLL -> the strided read is COALESCED.
- **#3/#4 bwd d_left/d_right (DLL->LLD), consumer = front_gatebwd_sm100._cdup_interleave**:
  ELIMINATED. `_cdup_interleave` already copies (grad->interleaved C operand); added a col-stride
  arg so it reads the M-major view `d_*_b.reshape(D,M).t()` directly (col stride != 1), fusing the
  transpose into that copy. gatebwd no longer forces `.contiguous()`.
- **#2 bwd d_tri (LLD->DLL), consumer = einsum-bwd cuBLAS batched gemm**: KEPT (genuine blocker).
  The einsum batches over D and contracts L. In LLD, D is the CONTIGUOUS (inner) dim but D is the
  BATCH dim -> the per-channel (L,L) matrix has strides (L*D, D): NEITHER dim is contiguous, so
  cuBLAS strided-batched-gemm cannot consume it (would copy internally). Same root cause as the
  v6 m-major-dgrad reduction blocker (producing d_tri as DLL needs the m-major dgrad epilogue,
  which transposes the LN row-reduction axis). So #2 keeps the fast tiled `_fast_T`.

## Correctness (train_recon, grads vs fp32) — PASS, unchanged (strided views = same values)
All tensors, all L: cos 0.99998-0.99999, relmean ~4.5-5.6e-3 (identical to v9). Graph gate:
graph grads == eager, worst_cos=1.000000 at every L.
