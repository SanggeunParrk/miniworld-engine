# trimul_train_b200 v3 — LN-backward fusion (dgrad_lnbwd / dab_lnbwd) sm100 port: BLOCKED

## Goal
Port the biggest-lever H100 fused backward kernels to sm100 tcgen05:
 - `dgrad_lnbwd` (back-half): fuse d_out_n = d_proj@Wp.T + LN_out-backward -> d_tri (removes the
   LN_out_bwd ~2.6 ms memory pass + the d_out_n HBM round-trip + an LLD<->DLL permute).
 - `dab_lnbwd` (LN_in): fuse the front d_xn GEMM + LN_in-backward -> dx.

## Attempt
Same recipe that worked for v2 (backward_gatebwd): subclass the mixin on `GemmSm100`
(`class _DgradLNBwdSm100(_DgradLNBwdMixin, GemmSm100)`), sm100 `default_config`, drive the
compile/launch path. Standalone dx-vs-torch spike.

## BLOCKER (specific, verified)
Unlike backward_gatebwd (built on the arch-AWARE `GemmGatedMixin`, no internal overrides), the
LN-bwd kernels override sm90-INTERNAL hooks that are structurally different on sm100:

1. `_compute_stages` arity mismatch (hard compile error):
   `_DgradLNBwdMixin._compute_stages(cls, cta_tile_shape_mnk, epi_tile, a_dtype, b_dtype,
     d_dtype, c_dtype, epilogue_args, smem_capacity, occupancy)`  = 10 params (sm90).
   `GemmSm100._setup_attributes` calls `_compute_stages` with 17:
     (tiled_mma, mma_tiler_mnk, cta_tile_shape_mnk, epi_tile, a_dtype, b_dtype, sf_dtype,
      sf_vec_size, d_dtype, c_dtype, d_layout, c_layout, epilogue_args, prefetch_A_idx,
      smem_capacity, occupancy).
   -> `TypeError: _compute_stages() takes 10 positional arguments but 17 were given`.

2. `_sm90_compute_tile_shape_or_override` (forces a SINGLE full-N epilogue subtile so the LN
   row-reduction over K is single-pass) is an sm90-only hook; the tcgen05 collective does not
   call it, so the single-subtile invariant the reduction depends on does not hold.

3. `epi_visit_subtile` FINALIZES the c1/c2 row-reduction IN-VISIT with
   `cute.arch.warp_reduction(..., threads_in_group=_LANES_IN_N=4)` — the SM90 WGMMA epilogue
   layout (4 lanes share an M row). The tcgen05 t2r fragment->lane mapping is different, so even
   if (1)+(2) are worked around, the hardcoded 4-lane reduce would give a partial/incorrect
   c1/c2 (the H100 bring-up notes record exactly this class of bug -> cos ~0.5).

=> Porting these two is a genuine sm100 epilogue BRING-UP (re-derive `_compute_stages` for the
   sm100 signature, re-derive the LN-row reduction for the tcgen05 epi_tile + lane layout,
   likely via `ColVecReduce.end` accumulate-across-subtiles instead of the in-visit finalize),
   NOT a base-class swap. quack DOES provide the sm100 primitives for it (colvec_reduce_accumulate
   / ColVecReduce have arch<100 branches; lanes_in_N is computed generically in ColVecReduce.end),
   so it is feasible but multi-iteration. Not completed this round.

## Status
No code committed for v3 (the naive port does not compile; a correct port needs the bring-up
above). Recorded as an honest blocker. v2 remains the best correct milestone (fwd+bwd L1024
18.67 ms; front-side backward 1.8x). The faithful port does not yet beat B200 cuequiv (6.93 ms);
the remaining gap is the memory-bound LN-backward passes + LLD<->DLL permutes that these two
kernels would fuse away.
