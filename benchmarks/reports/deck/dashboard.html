What changed from the previous kernel

PREVIOUS (tm1)

How it was built
개발 방식

The front GEMM uses quack's SM90 warp-specialized gated GEMM (TMA producer / WGMMA consumer, σ·mul fused in the epilogue); the bdll direct write needs an in-repo quack patch. We developed it iteratively with AI. The front GEMM already runs at ~67% of the HBM roofline — memory-bound and near-saturated — so the remaining lever is fusion, not GEMM-internal tuning. This is exactly where NVIDIA's second-stage tuning would add the most.

front GEMM은 quack의 SM90 warp-specialized gated GEMM(TMA 생산자 / WGMMA 소비자, epilogue에서 σ·mul 융합)을 사용하며, bdll 직접 기록에는 레포 내 quack 패치가 필요합니다. AI와 함께 반복적으로 개발했습니다. front GEMM은 이미 HBM roofline의 ~67%로 메모리 바운드·거의 포화 상태여서, 남은 레버는 GEMM 내부 튜닝이 아니라 융합입니다. 바로 이 지점에서 NVIDIA의 2차 튜닝이 가장 큰 효과를 낼 것입니다.

How it was built
개발 방식

A true single-kernel squeeze fusion (split-K atomic) is numerically correct but ~500–1000× slower (per-element atomicAdd). A fast fused squeeze needs a 2nd WGMMA in the epilogue — a large quack fork with no payoff at the model's d=128. So we ship triton b2b for d=128 and a cute-composed path for d≥256 (K-bound), where Triton's BLOCK_K scales badly.

진정한 단일 커널 squeeze 융합(split-K atomic)은 수치적으로는 정확하지만 per-element atomicAdd 때문에 ~500–1000× 느립니다. 빠른 fused squeeze에는 epilogue에 두 번째 WGMMA가 필요한데, 이는 quack의 큰 fork이면서 모델의 d=128에서는 이득이 없습니다. 따라서 d=128은 triton b2b, d≥256(K-bound)은 cute 조합 경로로 제공합니다. 후자에서는 Triton의 BLOCK_K 확장성이 떨어집니다.

TRACK 02

AF3-like model inference

AF3-like 모델 인퍼런스

AF3-like models hit a hard wall on a single GPU at roughly 1,000–3,000 residues — the pair representation is O(N²), and the network fires tens of thousands of un-fused kernels per step (≈37k linear, 25k LayerNorm, 12k activation — about 100× an LLM of the same size), so intermediates pile up in HBM. Existing fixes each pay a price. Our target: large inference on one ordinary GPU, without a cluster and without precision loss.

AF3-like 모델은 단일 GPU에서 대략 1,000–3,000 residue 수준에서 벽에 부딪힙니다. pair 표현이 O(N²)인 데다, 네트워크가 스텝마다 수만 개의 미융합 커널(linear 약 37k, LayerNorm 25k, activation 12k — 동급 LLM의 약 100배)을 띄워 중간 텐서가 HBM에 쌓이기 때문입니다. 기존 해법은 각각 대가를 치릅니다. 우리 목표는 일반 GPU 한 장에서, 클러스터 없이·정밀도 손실 없이 대규모 인퍼런스를 돌리는 것입니다.

Existing approaches & their limits

기존 방법과 한계

approach방법 idea아이디어 limitation한계
Fold-CP
NVIDIA BioNeMo · arXiv:2603.14806		 2-D context parallelism; shards the pair rep to O(N²/P). 4 GPUs → 3.6k residues; 256 GPUs → 20k tokens. 2-D 컨텍스트 병렬로 pair 표현을 O(N²/P)로 분산. 4 GPU → 3.6k residue, 256 GPU → 20k 토큰. Requires an H100/B200 cluster (dozens–hundreds of GPUs) — no help for single / few-GPU users. H100/B200 클러스터(수십~수백 장)가 필요 — 단일·소수 GPU 사용자에겐 무용.
MegaFold
arXiv:2506.20686		 Fused EvoAttention + DeepFusion (LN+Linear, SwiGLU) + AOT data cache. 1.23× memory, 1.73× step. 융합 EvoAttention + DeepFusion(LN+Linear, SwiGLU) + AOT 데이터 캐시. 메모리 1.23×, 스텝 1.73×. AF3 default · DeepMind docs		 Spill GPU memory to host RAM on overflow.메모리 초과 시 호스트 RAM으로 spill. Runs on 1 GPU but markedly slower (host bandwidth) — a stopgap. 1 GPU로 돌지만 현저히 느림(호스트 대역폭) — 임시방편.
FastFold / AutoChunk
PPoPP'24 · arXiv:2401.10652		 Auto-searched activation chunking — single A100 to ~10k residues, ~75% memory cut, ~5× inference. 자동 탐색 activation chunking — 단일 A100에서 ~10k residue, 메모리 ~75%↓, 인퍼런스 ~5×. AF2 training		 Scheduling + parallelism to cut multi-GPU communication.스케줄링+병렬화로 멀티-GPU 통신 절감. A training system — limited benefit at inference.학습 시스템 — 인퍼런스에는 이득 제한적.

arXiv:2505.05893		 Adaptive activation quantization to extend length.적응형 activation 양자화로 길이 확장. A precision tradeoff from quantization.양자화에 따른 정밀도 손실.
Why go further. Each line above solves one axis in a generic way: Fold-CP buys length with a cluster; FastFold/AutoChunk chunk activations op-agnostically (recompute overhead) and target AF2; quantization trades precision; the rest are training systems. None co-designs fused kernels + op-aware chunking for AF3 inference on a single GPU — and that is where the gains compound.
왜 더 나아가야 하나. 위 항목들은 각자 한 축을 범용적으로 풉니다 — Fold-CP는 클러스터로 길이를 사고, FastFold/AutoChunk는 op-무관하게 activation을 자른 뒤(recompute 오버헤드) AF2를 겨냥하며, 양자화는 정밀도를 내주고, 나머지는 학습 시스템입니다. 융합 커널 + op별 chunking을 AF3 단일 GPU 인퍼런스에 맞춰 공동설계한 사례는 없습니다 — 바로 거기서 이득이 곱해집니다.

What we'd build

우리가 만들 것

  • Chunking / streaming of the O(N²) pair representation
  • O(N²) pair 표현의 chunking / 스트리밍
  • CPU offload for cold tensors, overlapped with compute
  • cold 텐서의 CPU offload를 연산과 오버랩
  • Inference-only fused paths — fewer intermediates means less memory and less recompute than chunking alone
  • 인퍼런스 전용 융합 경로 — 중간 텐서가 줄어 chunking만 할 때보다 메모리와 recompute를 동시에 절감
  • No cluster; no quantization precision loss
  • 클러스터 불필요; 양자화 정밀도 손실 없음
cuEquivariance is not the speed ceiling — LayerNorm ≈ 1.0× at large d, and ours beats it 1.2–1.4× on TriMul. cuEquivariance는 속도 한계가 아닙니다 — 큰 d에서 LayerNorm ≈ 1.0×, TriMul에선 우리가 1.2–1.4× 능가.

Methodology & honest caveats

방법론 & 정직한 단서

  • All baselines are torch.compile'd PyTorch (never eager) — eager is launch-bound and an unfair reference.
  • 모든 기준선은 torch.compile PyTorch입니다(eager 아님) — eager는 launch-bound라 공정한 비교가 아닙니다.
  • H100 80GB, bf16, B=1. TriMul: D=128, single layer + mask; each kernel at its best regime (eager / compile / CUDA-graph). cuEquivariance & dt-v1 reproduce team-gm's harness.
  • H100 80GB, bf16, B=1. TriMul: D=128, 단일 레이어 + 마스크; 각 커널은 최적 regime(eager / compile / CUDA-graph). cuEquivariance·dt-v1은 team-gm 하네스를 재현합니다.
  • TriMul figures are forward-only; our backward is in development (within ~10% of dt-v1 at large L, ahead of cuEquivariance).
  • TriMul 수치는 forward 전용이며, backward는 개발 중입니다(큰 L에서 dt-v1의 ~10% 이내, cuEquivariance보다 앞섭니다).
