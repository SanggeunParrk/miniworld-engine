# Pairformer pair-track latency — H100 (sm90)

Generated by `benchmarks/runners/pairformer_compare.py` (3-way: pytorch / cuEquivariance / ours).
`pairformer_compare.py` is not part of the Hydra `bench.py` harness, so these are recorded here as
a markdown table rather than a CSV/SVG artifact.

- **Config:** B=1, d_pair=128, n_block=4, bf16, **CUDA graph (manual), no `--compile`**, p_drop=0.25.
- **ours:** autotuned via the in-repo shipped caches (parallel-captured per `module × mode × bucket`,
  merged). The full brute grid is kept buildable by the compile-monster guard (static
  `num_warps>=16`/`num_stages>=5` prune + a per-config fork-compile timeout backstop), not by
  hand-bounding any kernel's grid.
- **cuequiv (fair):** `CUEQ_TRITON_TUNING=ONDEMAND` (our shapes are already in cuequiv's shipped
  config cache, so ONDEMAND is a no-op — it was already tuned) **and** fed CONTIGUOUS inputs in
  cuequiv's native `(B, L1, H, L2, D)` layout (a strided rearrange view is ~35 % slower and would
  unfairly penalize the baseline).
- Times are the per-block-stack median (ms) over the `n_block=4` stack; `ours vs X` = X/ours (>1 = ours faster).
- All variants verified `cos_vs_pytorch = 1.000000` (inference check).
- Measured 2026-08-06 on node02 (H100 80GB HBM3, sm90), one job per (variant × mode × L) shape.
  Re-measured after the autotune-cache rebuild; numbers match the prior run within noise (no
  regression from the unified grids / newly-captured bwd caches).

### Reading the `full` vs cuequiv gap honestly

The `full` **`ours vs cuequiv`** ratio (up to 3.39× inference) is **not** a pure kernel-vs-kernel
number, and is larger than the trimul-only / per-kernel gaps for a structural reason:

- cuequiv only supplies the **attention and trimul CORES**. Under `CUEQUIVARIANCE` the surrounding
  ops — LayerNorm, the q/k/v projections, the output gate/`to_out`, **and the entire transition
  block** (which has *no* cuequiv kernel) — all fall back to **PyTorch**. So the cuequiv `full`
  number is dominated by unfused PyTorch glue, not by cuequiv kernels. (Feeding cuequiv contiguous
  inputs barely moves the `full` number — the attention *kernel* is a small slice of it.)
- ours fuses that glue (LN + projection + gate folded into the kernels), which is where most of the
  `full` win comes from.

**Pure kernel-vs-kernel margins** (the honest "our kernels vs cuequiv's kernels"):
- trimul core (trimul_only / trimul_dir): **~1.6–1.8×**.
- triangle-attention kernel, measured in isolation (L512, H=4, D=32, contiguous): **~1.57×**
  (ours 0.503 ms vs cuequiv 0.789 ms; the strided-rearrange wrapper made it look like 2.12×).

So: ours is genuinely faster at every level, but the `full` 3.4× is a **fusion** advantage, not a
3.4× faster attention/trimul kernel.
