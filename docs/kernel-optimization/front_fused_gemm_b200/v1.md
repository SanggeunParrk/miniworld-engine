# fused_front_gemm (sm100 B200) — v1: BW investigation (3 experiments, all NEGATIVE)

Optimization round on `FusedPreactGemmKernel` (`front_fused_gemm_sm100.py`), the v14 fused front
GEMM+GLU of the v6-faithful trimul TRAINING path (`V6TriMulMergedSm100`, node ② fwd). One
persistent CUTLASS Blackwell GEMM whose epilogue emits `lr[2H,M]` (GLU) + `preact[4H,M]`
(interleaved gate/proj, for the backward) via 3 TMA stores.

## Environment
- B200 (sm_100, cap 10.0), driver 580.95.05, torch 2.10.0+cu128, cutlass-dsl 4.4.2, bf16 in /
  fp32 acc / bf16 out. Repo `~/psk/miniworld-engine` @ cbd67f4. GPU0.
- ncu 2025.4 via `gcsudo` in tmux, `-k regex:FusedPreactGemm --set full -c 1` in the training NVTX
  PROFILE range (`~/psk/ncu/front_full.sh` → `sol_train_v12.py`). Correctness: `verify_v12.py`
  (grads) + a front-only `lr` cos check. Bench caveat: a standalone Python `do_bench` of
  `fused_front_gemm` reads ~34 ms (per-call `from_dlpack`/`HardwareInfo`/stream overhead), NOT GPU
  time — kernel time is read from ncu `Duration`.

## The question (why is it slow?)
The op is arithmetically trivial: 2 GEMMs (M=L²·N=256·K=128) ≈ 1.37e11 FLOP → ~62 µs of B200
compute; K=128 = single k-tile so tensor cores barely used (Compute 36%, TMEM 25%). It is
**memory(store)-bound**: writes ~1.9 GB (lr 0.54 GB + **preact 1.07 GB** + read A 0.27 GB),
arithmetic intensity ≈ 73 FLOP/byte ≪ 275 roofline crossover. Ideal BW-bound time (8 TB/s) ≈ 235 µs,
but it takes **612.9 µs at only ~52.7% DRAM (~3.5 TB/s)** — i.e. it does NOT saturate BW. Goal:
find why and push BW toward peak.

## Baseline profile (--set full, L=1024, 612.9 µs)
| metric | value |
|---|---|
| Compute / Memory / DRAM / L2 throughput | 35.8% / 60.4% / 52.7% / 44.9% |
| TMEM pipe | 25.2% ("well-utilized, not a bottleneck") |
| Registers/thread | 132 (Block Limit Regs = 2) |
| Dynamic smem/block | 229.5 KB — **16 C-stages (128 KB) + 2 AB-stages (96 KB)** |
| Achieved occupancy | **9.33% (1 CTA/SM, ~6 warps/SM)** |
| **No Eligible warp** | **64.95% of cycles** |
| dominant stalls | ~33% shared-scoreboard (bank conflict) + ~33% L1TEX/global (mem latency) |

Bank conflict: 2.18M conflicts = 14.75% of shared-store wavefronts.

## Root-cause theory
The kernel is memory-bound but strands BW because **occupancy is 1 CTA/SM → only ~6 warps → 65% of
cycles have NO eligible warp** to hide the store / shared / global latencies. So: raise occupancy
(more warps) → hide latency → higher achieved BW. What pins it to 1 CTA/SM?

## Experiments
**Exp 1 — independent register fragments (ILP).** The 3 per-subtile stores reused one `tRS_rC`
(serialized: store→copy→store→copy). Gave each its own fragment so the 3 r2s copies pipeline.
→ **NEGATIVE: 612.9 → 731.1 µs (0.84×)**; all throughputs dropped, occupancy unmoved. The compiler
already scheduled the reuse well; forcing 3 live fragments perturbed the epilogue. Reverted.

**Exp 2 — split smem for 2 CTA/SM** (`num_ab_stage=1` since K=128 is a single k-tile → no mainloop
overlap lost; cap C-stages so total smem ≤ ½). Achieved: **Block Limit Shared Mem 1 → 2**, but
**Achieved Occupancy stayed 9.33%** and time **690 µs (regressed)** — freeing smem did NOT add a
resident CTA (persistent kernel, grid = #SMs), it only shrank the store pipeline (16 → 8 stages).

**Exp 3 — Exp 2 + double the persistent grid** (`max_active_clusters ×2`). Correctness held. →
**Achieved Occupancy STILL 9.33%, Waves/SM = 1, 682 µs.** TMEM was still 512 (num_acc_stage=2) so
the 2nd CTA had no TMEM.

**Exp 4 — Exp 2/3 + halve TMEM** (`num_acc_stage=2→1` → `num_tmem_alloc_cols` 512→**256**, verified
by probe). Now TMEM(256) + smem(2) + grid(×2) ALL allow 2 CTA/SM. Correctness held (lr cos 1.0,
grads 0.999982). → **Achieved Occupancy STILL 9.32%, Waves/SM = 1, 863 µs (worst yet).** Even with
every named resource freed, only 1 CTA co-resides — and single-buffering the accumulator removed
the MMA/epilogue overlap the single CTA relies on → big regression.

## Conclusion — occupancy is pinned at 1 CTA/SM by the PERSISTENT SCHEDULER, not a freeable resource
This is a warp-specialized **persistent** kernel: 192 threads = 6 warps/CTA (1 tma + 1 mma + 4
epilogue), so its *theoretical* occupancy at 1 CTA/SM is exactly 6/64 = **9.38%** (achieved 9.33 =
already realized; there is no achieved-vs-theoretical gap to close). Getting to 12.5%+ needs a 2nd
resident CTA, but Exp 2–4 show that freeing every named limiter — smem (Block Limit Shared 1→2),
TMEM (512→256), and passing `max_active_clusters ×2` — does **not** add one: `Waves/SM` stays 1 and
occupancy stays 9.3%. The `StaticPersistentTileScheduler._compute_grid` sizes the grid to ≈#SMs
(148) and ignores the doubled `max_active_clusters`, so the hardware is only ever given 1 CTA/SM.
Every knob that freed resources for a hypothetical 2nd CTA instead weakened the pipelines the single
CTA depends on (num_acc_stage, C-stage depth) → monotonic regression (731 → 690 → 682 → 863 µs).

So the low occupancy is *by design* for this kernel class — it hides latency with async TMA/tcgen05
pipelines, not warps — and cannot be raised without **rewriting the persistent tile scheduler** to
launch and correctly map 2·#SMs CTAs (deep, correctness-risky; out of scope). The BW shortfall
(~52%) is therefore not fixable via occupancy here.

Remaining levers to exceed ~52% BW, in priority order:
1. **Cut store traffic (only >2× lever)** — `preact[4H]` (1.07 GB) is 56% of all bytes and exists
   only for `front_bwd_dW`; a compressed/absent preact contract drops the memory floor ~235 → ~100
   µs. Backward-contract change + precision re-validation.
2. **Rewrite the persistent scheduler for 2 CTA/SM** (now that TMEM can be halved to 256) — the only
   way to realize the occupancy fix; large, risky.
3. **Conflict-free epilogue smem swizzle** — removes the 14.75% shared-store conflict (shared half
   of the stall only); Exp 1 shows the epilogue schedule is fragile.

**Kept shipped kernel unchanged** (it is the fastest of all 5 variants tested). Recommendation:
revisit only via lever #1 (preact traffic).
