## Triton SASS Evidence

Disassembly of Triton's winning `_transition_b2b_kernel` shows the relevant memory instruction mix:

- Output store: `8x STG.E.128`.
- Input staging: `48x LDGSTS.E.BYPASS.128`; the inputs arrive through async 128-bit copy with L1 bypass.
- Shared-memory / matrix path: `16x STS.128`, `24x LDSM.16.M88.4`, `16x LDS.U16`.
- Math path: `HGMMA.64x64x16 x16` and `HGMMA.64x128x16 x4`, with async dependency barriers.

The important correction versus v10 is that Triton does stage through shared memory and uses `ldmatrix`; eliminating `xn` shared stores was the wrong target. v10 confirmed this empirically: it reduced `lg_throttle` but inflated raw LSU instruction count and regressed. The remaining principled lever is the final output store width.

## v11 Hypothesis

Replace the scalar global-output epilogue with a shared-memory shuffle that emits 128-bit row-contiguous global stores, matching Triton's output-store instruction width:

- First write the completed `out_acc` C-fragment into a row-major `WG_M x D` bf16 tile in shared memory.
- Synchronize the CTA so the tile is fully visible before reload.
- Reload the tile in fixed 8-bf16 chunks and issue inline PTX `st.global.v4.b32`.
- Keep vector packing out of the live accumulator path, avoiding v7's register spill failure mode.

Expected metric movement:

- SASS should show a small number of wide `STG.E.128` output stores instead of many scalar/narrow global stores.
- `lg_throttle` should drop versus v5 `1.58` if output stores are the dominant remaining LSU pressure source.
- `sm__inst_executed_pipe_lsu.sum` should fall versus v5 if the added smem shuffle costs less than scalar global-store issue.
- Registers should remain `255`; spill stores/loads should remain `0`.

## Epilogue Mapping

The store-to-smem phase uses the existing CuTe C-fragment coordinate tensor:

- For each owned accumulator slot `i`:
  - `m = get<0>(tCOut(i))`
  - `n = get<1>(tCOut(i))`
  - write `static_cast<BF>(out_acc(i))` to `pOutShuffle[m * 128 + n]`

The vectorized reload/store phase is deterministic and row-contiguous:

- `kOutVecsPerRow = D / 8 = 16`
- each consumer WG has `128` threads
- thread `wg_tid` handles `vec = wg_tid, wg_tid + 128, ... < 64 * 16`
- mapping:
  - `m = vec / 16`
  - `n = (vec % 16) * 8`
  - shared load: `ld.shared.v4.u32` from `pOutShuffle[m * 128 + n]`
  - global store: `st.global.v4.b32` to `out[row, n:n+8]`
- Row predication:
  - `valid = (wg_row0 + m) < M`
  - the vector store is predicated per 8-wide chunk; invalid tail rows use a harmless base pointer with predicate false.

Each output row is `128 bf16 = 256 B`, so every `8 bf16 = 16 B` group is naturally 16-byte aligned relative to a normally aligned contiguous output allocation.

### Verdict
**WIN — v11 is the new BEST (~1.20x vs Triton), committed.** The lever: replace v5's scalar per-element
output store (~64 scalar STG/thread) with Triton's proven vectorized **STG.128** via a smem-shuffle
epilogue (out_acc -> reuse dead `pXn` smem in row-major -> `ld.shared.v4` -> predicated
`st.global.v4.b32`). This was unlocked by the user lifting the "no PTX" constraint, and guided by the
Triton SASS ground truth (8x `STG.E.128`). It avoids v7's spill because the accumulator is written to
smem FIRST (freeing registers) before the vectorized reload+store.
