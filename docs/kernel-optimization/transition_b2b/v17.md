## v16 Regression Analysis

v16 fused the layernorm stats into the b2b CUDA kernel and preserved module correctness, but the module inference path regressed:

| Path | L | Module time | Correctness | Notes |
| --- | ---: | ---: | ---: | --- |
| stats_triton + b2b | 1024 | `1.30 ms` | TODO | Separate full-occupancy stats pass |
| Triton module path | 1024 | `1.57 ms` | TODO | Reference module baseline |
| v16 fused stats + b2b | 1024 | `2.05 ms` | module cos `0.999989` | Correct, no spill reported, but slower |

The fused-stats kernel removed a launch and a global input pass, but the reduction implementation serialized the critical prologue. In each warpgroup, only `wg_tid < WG_M` participated, so only 64 of 128 threads were active while the other 64 waited at the named barrier. Each active thread scanned one full row twice:

- pass 1: read `sXn(m, 0..127)` to compute `sum`
- pass 2: read `sXn(m, 0..127)` again to compute centered variance

That is 256 shared-memory scalar reads per active row thread, with 64 idle threads and one CTA/SM, so the latency cannot be hidden well. This serial row prologue can dominate the cheap separate `stats_triton` pass it was intended to replace.

## v17 Plan

Replace only the `FUSE_STATS` reduction block with a warp-cooperative row reduction. Keep the two-pass centered variance and all downstream normalization/GEMM code unchanged.

Expected benefit: reduce the row-stats work from 64 serial row scans to all 128 warpgroup threads participating, with four shared-memory reads per lane per pass and five warp shuffle steps per pass.

Expected risk: the added shuffle reduction and loop variables may increase register pressure from the v16/v14 high-water mark. If ptxas spills, this experiment likely loses even if the reduction itself is faster.

## Warp-Parallel Stats Design

Mapping:

- Warpgroup size: 128 threads = 4 warps.
- `WG_M=64` rows per warpgroup.
- `warp_id_in_wg = wg_tid / 32`.
- `lane = wg_tid % 32`.
- Each warp owns 16 rows:
  - warp 0: rows `0..15`
  - warp 1: rows `16..31`
  - warp 2: rows `32..47`
  - warp 3: rows `48..63`
- For each owned row `m`, lane `l` reads columns `l`, `l+32`, `l+64`, and `l+96` from raw row-major `sXn`.

Reduction:

1. The existing `cp_async_wait<0>()` completes x staging.
2. The existing fused-stats pre-reduction `NamedBarrier` remains so every thread sees the full `sXn` tile.
3. First pass:
   - each lane accumulates four bf16 values from `sXn(m, k)` into fp32 `sum`;
   - reduce with `__shfl_xor_sync(0xffffffffu, sum, offset)` for offsets `16, 8, 4, 2, 1`;
   - XOR reduction leaves the row total in all lanes, so all lanes compute the same `mean = total / 128`.
4. Second pass:
   - each lane rereads the same four columns;
   - accumulate `(x - mean) * (x - mean)` in fp32;
   - reduce again with the same five `__shfl_xor_sync` steps.
5. Lane 0 computes `rstd = rsqrtf(var + eps)` and writes `pRstd[cta_m]` and `pC1[cta_m] = mean * rstd`.
6. Invalid boundary rows write zero stats from lane 0 only.
7. The existing post-stats `NamedBarrier` remains so `pRstd/pC1` are visible before the normalization loop reads them.

The shared-memory access pattern is intentionally unswizzled: lanes read consecutive raw row-major columns, so each warp touches 32 consecutive `sXn(m, k)` elements per substep. The swizzled epilogue and normalized-xn storage are unchanged.

## Code Changes

- Replaced the v16 `if (wg_tid < WG_M)` one-thread-per-row stats loop with a warp-cooperative loop over `WG_M / 4` rows per warp.
- Used `__shfl_xor_sync` rather than shared-memory scratch or atomics.
- Kept the two-pass centered variance for parity with `stats_triton`.
- Kept both named barriers already present in v16.
- Left `transition_b2b_fwd` precomputed-stats entry and module wrapper wiring unchanged.

## Interpretation

This experiment fixes the obvious v16 prologue serialization. It does not guarantee a module win over the separate `stats_triton` path: the b2b CUDA kernel is constrained to one CTA/SM, while the standalone stats pass can run at much higher occupancy and may be cheap enough that launch removal is not decisive. The H100 module timing decides whether fused stats should stay wired into `cuda_transition_b2b` or whether the module should return to `stats_triton` plus the v14 precomputed-stats entry.

## Rollback

Rollback to the stats_triton module path if v17 fails to build, module cosine drops below `0.999`, ptxas reports stack/local spill, standalone precomputed-stats validation regresses, or module inference remains slower than the `1.30 ms` stats_triton path after the warp-parallel reduction.

## Validation + results (H100) — ❌ fused-stats loses to separate stats_triton; REVERTED
- Correct: module cos(cuda,torch)=0.999989, cos(cuda,triton)=1.000000; ptxas REG 255, STACK 0 (no spill).
- Warp-parallel reduction fixed v16's disaster (2.05->1.60 ms @ L=1024) BUT the fused-stats path is
  still SLOWER than doing stats as a separate kernel:

  | path | L=384 ms | L=1024 ms |
  | --- | ---: | ---: |
  | v16 fused-stats (naive serial) | 0.304 | 2.05 |
  | v17 fused-stats (warp-parallel) | 0.243 | 1.60 |
  | Triton-b2b | 0.244 | 1.57 |
  | **v14 + stats_triton (separate pass)** | **0.203** | **1.31** |

- **Verdict / negative result:** FUSE_STATS is the WRONG structure for the CUDA b2b. At 1 CTA/SM
  (8 warps) the on-chip stats reduction sits on the critical path and cannot be hidden, costing MORE
  than the separate `stats_triton` kernel which runs at full occupancy (bandwidth-bound, cheap) despite
  re-reading x from HBM. (Contrast: FUSE_STATS *won* for the Triton b2b, which has different occupancy.)
- **Action:** reverted the kernel + wrapper to the committed-good state (v14 kernel + stats_triton
  wrapper = 1.20x module inference). The fused-stats kernel entry was removed. Finding preserved here.
