## v0/v1 Evidence

- v0 (`bbae5b9`): hand CuTe fused b2b, two consumer warpgroups, inline TMA weight ring, `h` in registers. Runtime `658 us` at `M=524288`, `0.825x` of Triton `543 us`, cosine `1.0`.
- v0 ncu at `M=262144`: SM `31%`, occupancy `12.5%`, IPC `1.0`; stalls: wait `1.36`, lg throttle `1.40`, long scoreboard `0.79`, barrier `0.53`, GMMA `0.26`.
- v1 (`98dcc53`): hand-mirrored CUTLASS cooperative skeleton with one dedicated producer warpgroup plus two consumer warpgroups. Correctness passed with cosine `1.000000`, but runtime regressed to `752 us`, `0.717x` of Triton.
- v1 ncu: occupancy `14.2%`, `Block Limit Shared Mem = 1`, about `131 KB` shared memory, `384` threads/CTA, effectively `1 CTA/SM`; barrier rose to `2.12`, long scoreboard to `1.10`, lg throttle stayed high at `1.44`, GMMA improved to `0.15`.

## Bottleneck Theory

The v0 plateau is a coupled mainloop problem rather than a pure math-throughput limit. Weight movement, barrier timing, and GMMA issue are not balanced: wait and lg throttle are both high, GMMA still appears, and SM utilization is low despite a compute roofline estimate near `200 us`.

v1 showed that simply spending a whole producer warpgroup can lower visible GMMA stall, but the extra warpgroup and shared-ring synchronization cost more than they save. The remaining useful lesson is not "dedicate more threads to production"; it is "copy CUTLASS's tested pipeline ordering more faithfully while keeping the 2-WG fused b2b tile shape."

## v2 Plan / Hypothesis

Full `cutlass::gemm::collective::CollectiveMma` instantiation was not used in this round. The CUTLASS collective is built around one A/B GEMM mainloop with its own `SharedStorage` tensor layout. This kernel needs two expand GEMMs, a SwiGLU gate, and a second RS WGMMA squeeze without materializing `h`; forcing the full collective into that shape is a larger b2b collective port.

v2 instead adopts the exact SM90 collective pipeline pattern from CUTLASS while preserving the custom fused epilogue:

- Producer: `PipelineTmaAsync::producer_acquire`, `producer_get_barrier`, issue TMA copies, advance the producer state. TMA auto-arrives on the mbarrier; no explicit commit.
- Consumer: `consumer_try_wait`, `consumer_wait(token)`, run smem-sourced GMMA, `warpgroup_wait`, `warpgroup_fence_operand`, then `consumer_release`.
- Epilogue fusion: after expand accumulators `a` and `b` are ready, compute `h = swish(a) * b` in registers, cast to bf16 registers, and feed the RS WGMMA squeeze against `ws` in shared memory. `h` remains off HBM.

Expected metric movement: wait and GMMA stalls down versus v0, no v1-style barrier explosion, SM% up, and end-to-end runtime below Triton's `543 us` if the tail wait does not erase the overlap.

## Code Changes

- Added the CUTLASS collective declaration plus SM90 warp-specialized collective header:
  - `#include <cutlass/gemm/collective/collective_mma_decl.hpp>`
  - `#include <cutlass/gemm/collective/sm90_mma_tma_gmma_ss_warpspecialized.hpp>`
- Added `kMainloopMmasInFlight = 1` as the CUTLASS mainloop contract being mirrored for a two-stage pipeline.
- Replaced bare `weight_pipe.consumer_wait(tma_consumer_state)` with the CUTLASS tokenized sequence:
  - `auto weight_ready_token = weight_pipe.consumer_try_wait(tma_consumer_state);`
  - `weight_pipe.consumer_wait(tma_consumer_state, weight_ready_token);`
- Moved the squeeze GMMA tail wait before `consumer_release`.
  - v0 released the TMA stage immediately after queueing the squeeze GMMA and waited only after the loop.
  - v2 waits with `warpgroup_wait<0>()` and fences `out_acc` before releasing, because `ws` is an smem-sourced B operand and the next prefetch may overwrite that stage.
- Kept the 2 consumer warpgroups, `256` threads/CTA, `2` pipeline stages, `BN=64`, and dynamic shared memory at `131104` bytes.

## Correctness Risks

- The full `CollectiveMma` scheduler is not instantiated; this is a pipeline-ordering experiment. If performance does not move, the next real step is a larger custom b2b collective port.
- Waiting for the squeeze tail before release is more conservative than v0 and may reduce overlap. It should improve smem ownership correctness for `ws`, but it can raise wait/barrier time.
- `consumer_try_wait` token flow is copied from CUTLASS, but the producer remains a same-CTA single-thread TMA issuer rather than CUTLASS's full kernel-layer role split.
- The pipeline carries three weight tensors (`wa`, `wb`, `ws`) in one transaction, while CUTLASS `CollectiveMma` expects one A and one B operand. The transaction byte count remains `49152` bytes per stage.

## Rollback Criteria

- If cosine drops below `0.999`, revert v2 code and keep this document as failed analysis.
- If runtime is slower than v0 `658 us`, revert code unless ncu shows a clear single follow-up fix.
- If runtime beats v0 but remains above Triton `543 us`, keep only if ncu confirms wait/GMMA improved without a large barrier regression.

- Perf M=524288: v2 = **685 us = 0.792x** of Triton (543 us). v0 baseline = 658 us / 0.825x.
  => v2 REGRESSED slightly (more conservative CUTLASS tokenized wait/release reduced overlap).
- ncu M=262144: SM 30.7%, wait 1.36, lg_throttle 1.31, gmma 0.23, barrier 0.86, long_scoreboard 0.77
  — coupled stalls essentially UNCHANGED from v0. Adopting CUTLASS's pipeline pattern (short of a full
  CollectiveMma+fused-epilogue instantiation) did not move the wait/lg coupling.
- Verdict: REGRESSED — reverted to v0 baseline. Two CUTLASS-scheduler-inspired rounds (v1 cooperative
  skeleton, v2 pipeline pattern) both land below v0's 0.825x. The bundle lacks the b2b/two-tensor
  fusion collective, and a hand CollectiveMma+fused-epilogue port is research-grade.
- Next (v3): different axis — enlarge the expand wgmma N-tile (SM90_64x64x16 -> 64x128/64x256) to cut
  the wgmma instruction count (8 n-tiles -> 2-4) and improve tensor-pipe utilization (attack wait/gmma
  from the compute side, not the scheduler side).
