# transition_b2b - v5 LN global-load trim fallback

## Environment

- Branch: `b2b-cutlass-opt`
- Starting point / current best: v3 code from `7100053` per operator note; current file is v3-equivalent `BN=128`.
- Kernel: `src/miniworld_kernels/kernels/transition/cuda/transition_b2b_kernel.cu`
- GPU target: NVIDIA H100 80GB HBM3, `sm_90a`
- Local constraint for this edit: no GPU build, validation, benchmark, nsys, or ncu run here. H100 validation is delegated to the operator; do not commit this round.
- Shape under campaign: `M=524288, K=128, ND=512, D=128`, bf16 input/output, fp32 expand and squeeze accumulation.
- Contract kept: `transition_b2b_fwd(x,rstd,c1,g,beta,wa,wb,ws)->out`, current-stream launch, LN prologue folded, TMA weights, `h` in registers, RS WGMMA squeeze, no precision reduction.

## v3 Evidence

- v3: `SM90_64x128x16_F32BF16BF16_SS` expand, `BN=128`, `ND=512` in four chunks.
- Correctness: `cos(cuda, triton) = 1.000000`.
- Runtime at `M=524288`: `603.9 us = 0.898x` of Triton.
- v3 ncu at `M=262144`: registers `255`, stalls wait `1.39`, lg throttle `1.55`, GMMA `0.20`, barrier `0.67`, long scoreboard `0.65`.
- Interpretation: v3 won by halving expand WGMMA issue groups and loop count; the biggest remaining stall ratio is `lg_throttle`.

## Primary Hypothesis Checked

Requested experiment: keep v3's `64x128` expand tile, deepen the TMA weight pipeline by changing `wa/wb` from two stages to three stages, and single-buffer `ws` to free shared memory.

Feasibility math at `BN=128`:

- private `xn`: `2 * 64 * 128 * 2 B = 32768 B`
- one `wa/wb` stage: `(128 * 128 + 128 * 128) * 2 B = 65536 B`
- three `wa/wb` stages: `196608 B`
- one `ws` stage: `128 * 128 * 2 B = 32768 B`
- tensor smem before barriers: `32768 + 196608 + 32768 = 262144 B`

That exceeds the H100 per-block dynamic shared-memory opt-in cap used by this kernel (`227 KiB = 232448 B`) before pipeline storage. It also cannot preserve `2 CTAs/SM` because the two-CTA target is about `113 KiB` per CTA. Therefore the deeper `wa/wb` ring is infeasible for this tile without reducing tile shape or removing a materially larger smem allocation.

## Fallback Hypothesis

Attack `lg_throttle` by removing repeated scalar global loads from the LN prologue.

Before v5, each CTA loaded:

- `g[k]` and `beta[k]` from global for every row vector in both warpgroups, even though they are invariant across rows.
- `rstd[row]` and `c1[row]` once per 8-element `K` vector, so each row reloaded those scalars repeatedly.

v5 stages those LN parameters once per CTA into the remaining shared-memory slack:

- `g[128]` and `beta[128]` as bf16: `512 B`
- `rstd[128]` and `c1[128]` as fp32: `1024 B`
- total added smem: `1536 B`

Expected metric movement: lower per-thread global/LSU pressure in the prologue and possibly lower `lg_throttle`. Risk is that extra smem traffic and the added CTA-level `__syncthreads()` offset the saved global loads.

## Code Changes

- Kept v3 tile and WGMMA atoms:
  - `kBn = 128`
  - expand `SM90_64x128x16_F32BF16BF16_SS`
  - squeeze `SM90_64x128x16_F32BF16BF16_RS`
- Kept the existing weight ring:
  - `wa/wb/ws` remain in one `PipelineTmaAsync<2>` ring.
  - No `ws` single-buffer path was added because the requested 3-stage `wa/wb` design is over the per-block smem cap.
- Added dynamic-smem slots after the staged weights:
  - `pG`, `pBeta`, `pRstd`, `pC1`
- Loaded `g`, `beta`, `rstd`, and `c1` once per CTA while `x` cp.async is outstanding.
- Reused the staged LN parameters in the normalization loop.

## Smem / Occupancy

- CTA threads: `256` (`2` warpgroups x `128` threads)
- Consumer warpgroups: `2`
- Expand tile per consumer WG: `64 x 128 x 128`
- Weight pipeline stages: `2`
- `ws` stages: `2` inside the same weight ring
- TMA transaction per stage:
  - `wa`: `128 * 128 * 2 B = 32768 B`
  - `wb`: `128 * 128 * 2 B = 32768 B`
  - `ws`: `128 * 128 * 2 B = 32768 B`
  - total: `98304 B` (`96 KiB`)
- Tensor shared memory:
  - two private `xn` tiles: `32768 B`
  - two weight stages: `196608 B`
  - staged LN params: `1536 B`
  - total tensor smem: `230912 B`
- Pipeline storage: `32 B`
- Dynamic shared memory: `230944 B` (`225.53 KiB`)
- Expected CTA residency: shared-memory limited to `1 CTA/SM`. This remains under the H100 opt-in cap but is far above the two-CTA target.

## Rollback Criteria

- If build fails or cosine is below `0.999`, revert code to v3.
- If runtime is slower than v3 `603.9 us`, revert code to v3 and keep this doc as a negative result.
- If runtime is neutral but `lg_throttle` improves, keep only if a follow-up can exploit the saved LSU pressure without adding more barriers or smem.
- If `lg_throttle` does not move, the remaining stall is likely dominated by TMA/GMMA issue structure rather than the LN prologue scalar loads.
