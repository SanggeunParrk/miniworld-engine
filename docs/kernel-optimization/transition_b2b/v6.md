## v5 Evidence

- v5: `563.3 us = 0.956x` of Triton `538 us`, `cos(cuda, triton) = 1.0`.
- v5 ncu at `M=262144`: long scoreboard `0.13`, GMMA `0.22`, barrier `0.81`, wait `1.35`, lg throttle `1.58`; Triton lg throttle `0.00`.
- Interpretation: v5 successfully hid normal global-load latency by staging LN parameters into shared memory, but still leaves large LSU / issue-queue pressure. The dominant remaining suspicious path is the LN prologue's per-thread `x` load and shared-memory transform path, not the weights, because `wa/wb/ws` are already TMA.

## LG-Source Theory

Before v6, each CTA still did the raw `x` tile load through per-thread 128-bit `cp.async`:

- two consumer warpgroups each loaded a `64 x 128` bf16 tile of `x`;
- `cp_async_16` called a raw `smem_addr_u32` helper, which emitted `cvta.to.shared`;
- the LN transform used raw `ld.shared.v4.u32` and `st.shared.v4.u32` helpers around the same swizzled shared tile.

That path is the most likely remaining `lg_throttle` source: many per-thread LSU instructions, plus explicit shared-address conversion in the hot prologue. It is also exactly the class of traffic Triton avoided in the provided NCU comparison.

The output store remains a secondary suspect. The current epilogue still assigns CuTe fragment elements to `tGOut(i)`, so NCU/SASS must confirm whether that lowers to vectorized coalesced stores or scalar STG. This round intentionally leaves the output store unchanged so the profiler can isolate the x/LN-prologue experiment.

## v6 Fix

Focused experiment: replace the per-thread global `x` load path with x TMA and remove the raw PTX shared-memory helpers from the LN path.

Code changes:

- Added a one-stage `XPipeline = cutlass::PipelineTmaAsync<1>`.
- Added a host-side TMA descriptor for `x` as row-major `(M, 128)` bf16, tiled as `64 x 128`.
- In each CTA, thread 0 issues two x TMA loads on one x mbarrier:
  - warpgroup 0 tile: rows `[blockIdx.x * 128, +64)`;
  - warpgroup 1 tile: rows `[blockIdx.x * 128 + 64, +64)`.
- Removed the raw PTX helpers from the file:
  - `smem_addr_u32`
  - `cp_async_16`
  - `smem_load_u128`
  - `smem_store_u128`
  - the unused CuTe cp.async helper
- The LN transform waits on the x TMA pipeline, then reads/writes the swizzled `sXn(m,k)` tensor in place with CuTe tensor access.
- Kept v5's staged `g`, `beta`, `rstd`, and `c1` shared-memory loads.

Expected metric movement:

- `sass__inst_executed_global_ld` / cp.async-related per-thread x load issue should drop sharply.
- `cvta.to.shared`, manual `ld.shared.v4`, and manual `st.shared.v4` from the LN helper path should disappear.
- `lg_throttle` should move down if the LN prologue was the dominant source. Target is a clear drop from v5 `1.58`; if it stays high, check output-store STG and local-memory spill counters next.

## Smem / Occupancy

- Consumer warpgroups: `2`
- Expand tile per consumer WG: `64 x 128 x 128`
- Weight pipeline: unchanged `PipelineTmaAsync<2>` for `wa/wb/ws`

- Weight pipeline storage: `32 B`

- Expected CTA residency: unchanged, shared-memory limited to `1 CTA/SM`.

## Register / Spill Notes

- If the extra TMA descriptor/pipeline state causes spills, lg throttle may get worse despite removing per-thread global x loads.
- Required NCU counters: local load/store instruction counts, local memory sectors, and ptxas spill stores/loads.

## Risks / Rollback

- Correctness risk: x TMA descriptor tiling and the single x mbarrier sequence are new. The logical mapping is two `64 x 128` warpgroup tiles per CTA, but H100 verification must confirm no tile-coordinate or barrier-phase mistake.
- Performance risk: the LN transform now uses CuTe tensor element access instead of the previous manual 128-bit shared load/store helpers. This removes raw address-conversion and manual LSU instructions, but ptxas may lower the element loop to more scalar shared-memory instructions. NCU/SASS decides whether that tradeoff helps.
- Register risk: the extra x TMA descriptor/pipeline state may create spills at v5's already-tight 255-register budget.
- Roll back to v5 if build fails, cosine drops below `0.999`, ptxas reports local-memory spills, or runtime regresses without a meaningful `lg_throttle` decrease.
