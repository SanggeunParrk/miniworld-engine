## Hypothesis

The remaining LSU-side suspects in v5 are:

- `xn` shared-memory stores, already explicit 128-bit `st.shared.v4.u32`;
- the raw `x` global load, which regressed when converted to TMA in v6;
- the final `out_acc -> out` global store.

This round attacks only the output store. The source epilogue previously assigned individual CuTe C-fragment elements to `tGOut(i)`, leaving vectorization to compiler lowering. v7 makes the intended store explicit:

- each consumer warpgroup writes its `64 x 128` bf16 output tile;
- each row is contiguous row-major, `128 * 2 B = 256 B`, so every 8-column bf16 span is naturally 16-byte aligned when the output allocation is at least 16-byte aligned;
- each thread packs owned contiguous 8-column spans into a `uint4`;
- the store helper emits predicated `st.global.v4.b32`, which should lower to `STG.E.128`.

Expected metric movement: fewer or cleaner global-store issue instructions in the epilogue and a modest drop in `lg_throttle`. This is a small lever; the needed gain to beat Triton is about 4.5 percent from v5.

## Code Changes

- Added `global_store_u128(void*, uint4, bool)` using inline PTX:
  - `@p st.global.v4.b32 [ptr], {r0,r1,r2,r3}`
  - expected SASS: predicated `STG.E.128`
- Added an `OutVec` packer for 8 bf16 values (`8 * 2 B = 16 B`).
- Replaced the scalar-only epilogue with:
  - vector path for complete per-thread `(m, n..n+7)` spans where `n % 8 == 0`;
  - scalar fallback only if a thread's C-fragment layout does not contain a complete 8-column span.
- No shared-memory epilogue tile was added.
- No changes to x loading, LN staging, TMA weights, WGMMA atoms, launch shape, host signature, or precision.

## Risks / Rollback

- Register risk: v5 is already at 255 registers/thread. The vector packer may increase register pressure or create local-memory spills, which would directly contradict the goal.
- Compiler risk: inline PTX should force `st.global.v4.b32`, but final SASS still needs confirmation as `STG.E.128`.
- Layout risk: if the C-fragment ownership is not complete 8-column spans per thread, the scalar fallback preserves correctness but the optimization will not move the metric.
- Performance risk: if v5 was already auto-vectorized, this explicit pack path may be neutral or slower due to added predicate/search work.

Rollback to v5 if build fails, cosine drops below `0.999`, local-memory spill appears, runtime regresses, or SASS shows scalar output stores still dominate.

## Next Idea If Needed

If v7 does not beat Triton and confirms output stores were already vectorized or not the source of `lg_throttle`, the next credible lever is register-pressure reduction around the epilogue and `h_bf` handoff. The goal would be to keep spill at zero while giving ptxas room below the 255-register ceiling, not to reduce precision or TMA the x path again.

  (local ld/st) -> lg_throttle worse + slow. The STG.128 intent backfired via reg pressure.
