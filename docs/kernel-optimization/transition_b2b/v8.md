# transition_b2b - v8 reusable one-tile weight smem for 2 CTA/SM

## Environment

- Branch: `b2b-cutlass-opt`
- Starting point / current best: v5, commit `7528d0d`
- Kernel: `src/miniworld_kernels/kernels/transition/cuda/transition_b2b_kernel.cu`
- GPU target: NVIDIA H100 80GB HBM3, `sm_90a`
- Local constraint for this edit: no GPU build, validation, benchmark, nsys, or ncu run here. H100 validation is delegated to the operator; do not commit this round.
- Shape under campaign: `M=524288, K=128, ND=512, D=128`, bf16 input/output, fp32 expand and squeeze accumulation.
- Contract kept: `transition_b2b_fwd(x,rstd,c1,g,beta,wa,wb,ws)->out`, current-stream launch, LN prologue folded, TMA weights, `SM90_64x128x16` expand, RS WGMMA squeeze with `h` in registers, persistent `out_acc`, two consumer warpgroups, no precision reduction.

## v5 Diagnosis

- v5: `563.3 us = 0.956x` of Triton `538 us`, `cos(cuda, triton) = 1.0`.
- v5 ncu: dynamic shared memory `230944 B`, registers/thread `255`.
- Occupancy/resource cap: Block Limit Shared Mem `1`, Block Limit Registers `1`, achieved occupancy `11.83%`.
- Interpretation: v5 is close to Triton despite running at `1 CTA/SM`. The low instruction count from the `64x128` expand tile is good; the next experiment should try to preserve that tile while reducing per-CTA smem enough for `2 CTAs/SM`.

## Hypothesis

The requested direction was to drop the weight ring from two stages to one stage. A literal one-stage ring with resident `wa`, `wb`, and `ws` tiles would be:

- `xn`: `128 * 128 * 2 B = 32768 B`
- `wa + wb + ws`: `3 * 128 * 128 * 2 B = 98304 B`
- staged LN params: `1536 B`
- tensor smem before pipeline storage: `132608 B`

That is much lower than v5 but still above the practical `2 CTA/SM` target of about `112-114 KiB` per CTA. Therefore v8 uses one reusable `128x128` TMA weight buffer instead of one resident tile for each of `wa`, `wb`, and `ws`.

Expected upside: dynamic smem falls to about `67 KiB`, so shared memory should no longer cap residency at one CTA. Register residency is the hard validation point: this kernel launches `256` threads (`2` warpgroups), so `255` regs/thread would still permit only `1` CTA by registers (`255 * 256 = 65280` regs for one CTA). True `2 CTA/SM` residency requires ptxas to cut the kernel to roughly `<= 128` regs/thread or an additional register-reduction round.

Expected downside: weight load hiding is weaker. v5 had a two-stage ring and all three weight operands resident per stage; v8 serializes `wa`, `wb`, and `ws` TMA loads through one buffer. The bet is that `2 CTAs/SM` hides the extra TMA wait better than v5's `1 CTA/SM` can.

## Code Changes

- Changed `kPipelineStages` from `2` to `1`.
- Replaced resident `pWa`, `pWb`, and `pWs` smem regions with one reusable `pWeight` tile.
- Changed TMA transaction bytes from one combined `wa+wb+ws` stage (`98304 B`) to one `128x128` bf16 tile (`32768 B`).
- For each `ND` chunk:
  - TMA load `wa` into `pWeight`, wait, compute `a_acc`, release.
  - TMA load `wb` into `pWeight`, wait, compute `b_acc`, release.
  - TMA load `ws` into `pWeight`; while it is in flight, compute `h` and convert to bf16; wait, run squeeze GMMA, release.
- Kept the same `SM90_64x128x16` expand and squeeze atoms, same `xn` shared-memory staging, same staged LN params, same host signature, same stream behavior, and same bf16/fp32 precision policy.

## Smem / Occupancy

- `xn` smem: `32768 B`
- reusable weight smem: `32768 B`
- staged LN params: `1536 B`
- Tensor shared memory: `67072 B`
- Pipeline storage: `align16(sizeof(PipelineTmaAsync<1>::SharedStorage))`, asserted `<= 32 B`
- Expected dynamic shared memory: `<= 67104 B`
- Expected shared-memory CTA limit: at least `2 CTAs/SM`
- Register limit: v5 had `255` regs/thread with a `256`-thread CTA, which allows only `1` CTA by registers. v8 needs a large ptxas register reduction to `<= 128` regs/thread for true `2 CTAs/SM`; otherwise this round only removes the shared-memory limit.

## Risks / Rollback

- TMA overlap risk: this is more aggressive than a literal one-stage ring. `wa`, `wb`, and `ws` loads are serialized through one buffer, so long scoreboard or wait stalls can rise.
- Register risk: v5 is far above the `2 CTA/SM` register target for a 256-thread CTA. If v8 does not naturally drop to `<= 128` regs/thread, the shared-memory cut alone will not deliver the intended occupancy.
- Pipeline risk: the single pipeline is reused three times per `ND` chunk. H100 validation must confirm the acquire/wait/release phase sequence is correct.
- Correctness risk: `wa/wb` and `ws` use different logical tensor views over the same 128x128 swizzled buffer. The layouts have the same element count, but the final proof is the H100 cosine check.

Rollback to v5 if build fails, cosine drops below `0.999`, registers remain the limiting factor without a compensating runtime gain, spills appear, or runtime regresses because the lost TMA overlap dominates the shared-memory relief.

## Validation + results (H100) — REGRESSED
- cos 1.0; Perf M=524288: v8 = **786.7 us = 0.684x** (v5 = 563.3us/0.956x). REGRESSED.
- Cause + KEY insight: 256 threads x 255 regs = 65280 -> REGISTERS cap at 1 CTA/SM regardless of smem.
  So reducing smem did NOT yield 2 CTAs, and 1-stage weights LOST load-hiding -> regressed. We are
  ALREADY at Triton's occupancy (~8 warps/SM). More occupancy is not achievable at the 64x128 tile
  (255 regs). The ONLY remaining gap to Triton is lg_throttle 1.58 (Triton 0), pure LSU throughput.
- Verdict: REVERTED to v5. Next (v9): cut LSU ops directly — the 163,840 xn shared-stores (STS) are a
  big LSU source; keep xn in REGISTERS (LN output -> wgmma A fragment, no smem round-trip) to remove
  them, like the h-in-registers trick applied to xn.
