# transition_b2b - v9 register-resident xn expand

## Environment

- Branch: `b2b-cutlass-opt`
- Starting point / best: v5, commit `7528d0d`
- Kernel: `src/miniworld_kernels/kernels/transition/cuda/transition_b2b_kernel.cu`
- GPU target: NVIDIA H100 80GB HBM3, `sm_90a`
- Local constraint for this edit: no H100 runtime validation, benchmark, nsys, or ncu run here. H100 validation is delegated to the operator; do not commit this round.
- Shape under campaign: `M=524288, K=128, ND=512, D=128`, bf16 input/output, fp32 expand and squeeze accumulation.
- Contract kept: `transition_b2b_fwd(x,rstd,c1,g,beta,wa,wb,ws)->out`, current-stream launch, TMA weights, `SM90_64x128x16` expand tile, RS WGMMA squeeze with `h` in registers, persistent `out_acc`, two consumer warpgroups, no precision reduction.

## v5 Evidence

- v5: `563.3 us = 0.956x` of Triton `538 us`, `cos(cuda, triton) = 1.0`.
- v5 ncu: `lg_throttle = 1.58`, Triton `lg_throttle = 0`; local memory load/store and spills were reported as `0`.
- v8 showed occupancy is already effectively at Triton's regime: reducing smem did not get `2 CTA/SM` because `256 threads * 255 regs = 65280` registers/CTA keeps registers as the hard limit.
- Remaining gap is therefore LSU throughput, not occupancy or spilling.
- Operator-provided v5 NCU symptom: `163,840` shared stores, with a large source being the LN prologue writing `xn` to smem before every expand chunk reloads it as the A operand.

## Hypothesis

Remove the `xn` shared-memory round trip:

- Change expand from `SM90_64x128x16_F32BF16BF16_SS` to `SM90_64x128x16_F32BF16BF16_RS`.
- Build the expand A register fragment once per warpgroup from the LN result.
- Reuse that `xn` fragment for both `wa` and `wb` GEMMs across all four `ND` chunks.

Expected metric movement:

- The explicit `st.shared.v4.u32` LN output store disappears.
- The expand A-side shared-memory descriptor / ldmatrix path disappears.
- `lg_throttle` should fall if the removed shared-memory traffic was the dominant LSU source.

Primary risk: v5 was already at `255` regs/thread. Holding `xn` in registers can either stay capped at `255` through compiler scheduling or spill. Any local memory load/store in ptxas/NCU defeats this round.

## Code Changes

- Removed the resident `xn` shared-memory allocation:
  - dynamic smem drops from `230944 B` to `198176 B`.
  - `pWa` now starts at the beginning of dynamic smem.
- Removed the `x -> sXn` cp.async staging and `sXn <- xn` shared-store prologue.
- Changed expand MMA:
  - old: `SM90_64x128x16_F32BF16BF16_SS`
  - new: `SM90_64x128x16_F32BF16BF16_RS`
- Constructed `xn_frag` using the expand MMA's own A-fragment layout:
  - `sXnLayoutOnly` is a layout-only BF operand view over `lXn`; it is not used as storage for `xn`.
  - `thrE.partition_fragment_A(sXnLayoutOnly)` gives the RS A register layout expected by the expand WGMMA.
  - `make_identity_tensor((WG_M,K))` plus `thrE.partition_A(...)` gives the logical `(m,k)` for each fragment slot.
  - each slot computes `(x[row,k] * rstd[row] - c1[row]) * g[k] + beta[k]`, casts to bf16, and stores directly into `xn_frag`.
- Reused `xn_frag` in the ND loop:
  - `cute::gemm(mmaE, xn_frag, tWaB, a_acc)`
  - `cute::gemm(mmaE, xn_frag, tWbB, b_acc)`
- Kept the v5 two-stage resident TMA weight ring for `wa/wb/ws`, staged LN params, and the existing RS squeeze path.

## Risks / Rollback

- Correctness risk: the identity-coordinate partition must match the expand A register slots. The local compile proves the layout is legal, but only H100 cosine proves the slot mapping is semantically correct.
- Register risk: the candidate remains at the `255` register ceiling. If H100 reports spills or local memory traffic, revert to v5.
- Load risk: direct global loads of `x[row,k]` now fill the RS fragment. This removes shared-memory traffic but may increase scalar global-load instruction count; NCU must decide whether the LSU mix improves.
- Roll back to v5 if build fails, cosine is below `0.999`, local memory appears, `lg_throttle` does not improve, or runtime regresses.

## Validation + results (H100) — NEUTRAL (~tie, kept v5)
- cos 1.0; Perf M=524288: v9 = **571.6 us = 0.950x** vs v5 563.3us/0.956x. Within noise / marginally
  worse. cuobjdump: STS 163840->4, LDSM->0 (xn smem round-trip ELIMINATED), regs 255, smem 230->198KB.
- KEY: removing the xn shared-store/reload did NOT reduce runtime => the xn STS was NOT the lg_throttle
  source (direct global x LDG replaced the STS traffic). lg_throttle remains ~1.58 and UNPINNED after
  4 distinct attacks (v6 x-TMA, v7 output-store, v8 occupancy, v9 xn-in-registers).
- Verdict: kept v5 (best, 0.956x). lg_throttle is a robust ~5% ceiling: we are at Triton's occupancy
  (8 warps/SM), no register spill, loads hidden (long_sb 0.13) — the residual LSU-throughput gap to
  Triton's tuned instruction schedule resists hand cuts.
