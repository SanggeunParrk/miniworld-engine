# transition_b2b sm100 (B200) — v1: bring-up + module integration (split: expand+SwiGLU / cuBLAS squeeze)

First round of the Hopper→Blackwell port of the fused Transition forward. Establishes a CORRECT
sm100 path, wires it into BOTH the inference and training dispatch, and benchmarks inference AND
training (fwd+bwd) per the repo convention.

> **Correction (supersedes the first draft of this doc):** an earlier version claimed "1.40×". That
> compared the sm100 path with LN EXCLUDED (xn precomputed) against the Triton path with LN INCLUDED
> — not apples-to-apples. **Retracted.** The honest, module-level (LN-included) numbers are below:
> inference **1.19–1.29×** over Triton; training ≈ **1.02–1.03×** (backward-bound). See tables.

## Environment
- NVIDIA B200, sm_100 (cap 10.0), dev box "B200_2". CUDA 13.1. torch 2.10.0+cu128, cutlass-dsl 4.4.2
  (pixi `.pixi/envs/default`, python3.12). Repo `~/psk/miniworld-kernels`.
- bf16 in / fp32 acc / bf16 out. No precision reduction. Shapes (n=4): (K,ND,D)=(128,512,128),(256,1024,256).
- Perf = CUDA-graph replay median (naive do_bench of the DSL wrapper measures host overhead, not GPU
  time). L∈{384,512,768,1024}, M=L² (pair rep). Deployment is CUDA-graph captured.

## Why a rewrite, not a recompile
H100's b2b fed the SwiGLU intermediate straight from registers into a register-source (RS) WGMMA
squeeze. Blackwell tcgen05 has NO register-operand MMA (A from smem/TMEM only), so the RS trick is
architecturally impossible; the b2b becomes a warp-specialized DSL kernel with a smem/TMEM h
round-trip (fusion = Round 2). No raw-.cu tcgen05 precedent exists in-repo — all sm100 kernels are
cutlass-DSL, so we mirror trimul.

## v1 approach (staged)
Reuse the tuned trimul `GatedPersistentGemmKernel` (`tm1/cute/sm100_gate_gemm_collective.py`), which
computes `sigmoid(A@Bg^T)*(A@Bp^T)` (dual-B, dual-TMEM-acc, TMA-store epilogue). SwiGLU differs by ONE
factor: `silu(gate)·proj = gate·σ(gate)·proj`. New file `transition/cute/b2b_fwd_sm100.py`:
- `SwiGLUExpandKernel(GatedPersistentGemmKernel)`: overrides only `_gated_epilogue`; `ov = p*σ(g)` →
  `ov = g*p*σ(g)`. Everything else inherited.
- `swiglu_expand_gemm(xn, wb, wa)` → `h[M,ND] = silu(xn@wa^T)*(xn@wb^T)` (Bg=wa gate/silu, Bp=wb up).
- `transition_b2b_sm100(xn, wa, wb, ws)` = expand kernel + **cuBLAS squeeze** `torch.mm(h, ws.t())`.
- `transition_b2b_sm100_ln(x, ln_w, ln_b, wa, wb, ws, eps)` = optimized `layernorm_kernel` (repo's
  tuned HBM-bound LN) → xn → the above. **LN uses the tuned kernel, NOT a torch affine** (a torch fp32
  affine cost ~0.3–0.5 ms and made sm100 lose; the tuned LN makes xn a cheap ~2-pass extra).

## Integration (both dispatches)
- Inference: `transition_b2b_sm100_ln` is the module-equivalent forward (LN + expand + squeeze).
- Training: wired into `TritonTransitionFusedFunction.forward` (`transition/triton/fused.py`) — on
  cap==10 the sm90 hand-CUDA `transition_b2b_fwd` (which can't build on B200) is replaced by
  `transition_b2b_sm100_ln`. The **Version A backward is arch-agnostic Triton** (recomputes xn from
  saved stats), so it works unchanged with the sm100 forward. H100 path (cap 9) untouched.

## Validation
- Forward (vs fp32 torch `(silu(xn@wa^T)*(xn@wb^T))@ws^T`): d=128 out cos 0.999997, d=256 0.999997.
- Training (sm100 fwd + Version A Triton bwd, vs pytorch autograd): d=128 & d=256 —
  out/dX/dWa/dWs cos all **0.99999**. Grads correct.

| L | M | pytorch | triton | **sm100** | sm100 vs triton |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 384 | 147456 | 1.283 | 0.771 | **0.754** | 1.02× |
| 512 | 262144 | 2.193 | 1.311 | **1.274** | 1.03× |
| 1024 | 1048576 | 18.25 | 12.80 | **12.63** | 1.01× |

d=256 (Triton training OOMs on B200): sm100 = 4.35 / 8.28 / 17.1 / 27.8 ms → only working path.

Training win is marginal because the **Version A backward (Triton) dominates fwd+bwd and is shared**
between the triton and sm100 rows; only the forward's ~0.02 ms saving carries. **To speed up training
meaningfully, the backward must be sm100-ized** (separate, larger effort).

## Profile (ncu, expand kernel, d=128 M=262144; clocks locked → absolute Duration > graph time)
DRAM 31.4% / SM 49.7% / occupancy 9.31% (1 CTA/SM, 192 thr = 6 warps), 198 regs, 1 block/SM, 1 wave.
Neither DRAM nor compute saturated → latency/occupancy-bound at 1 CTA/SM (same signature as the
front_fused sm100 kernel). Not DRAM-bound → the fusion win comes from removing the h HBM round-trip.

## Why the sm100 gain is modest so far, and where the headroom is
The H100 hand-CUDA b2b climbed from **0.825× (slower than Triton) over ~14 rounds to 1.29×** (v0→v14:
epilogue STG.128 vectorize, bank-conflict swizzle, WG-local barriers, gamma/β register-load). We START
at ~1.2× on round 1 because we reuse the already-tuned trimul collective. Crucially, **v1 is still
SPLIT (cuBLAS squeeze, h round-trips HBM)** — the squeeze is ~32% of the split time. On H100 the
FUSION itself was the headline lever (b2b 112µs vs split 211µs ≈ **1.9×**, since not fusing means you
must re-read h). So most of the remaining gain is in fusion, not yet done here.

## Next (rounds)
1. **Round 2 — true fused b2b**: 2nd tcgen05 MMA `out=h@ws^T` inside the kernel (M-persistent + ND-loop:
   expand→silu→r2s sH→squeeze-accumulate into a 3rd TMEM acc). Kills the h round-trip. Biggest lever.
2. Fuse the LN affine into the kernel A-load (H100-style) to drop the separate xn pass.
3. sm100 backward (Version A is Triton) to make TRAINING gain more than marginal.
4. sm100-specific tuning (epilogue depth, AB/C stages, occupancy) — analogous to H100 v11–v14.
