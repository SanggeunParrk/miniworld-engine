# transition_b2b sm100 (B200) — v3: fused-vs-split campaign — FINAL (ship the split)

Exhaustive attempt to make the TRUE FUSED transition b2b (expand→SwiGLU→squeeze in ONE
kernel, no h HBM round-trip) beat the SPLIT (DSL expand+SwiGLU kernel → h → cuBLAS squeeze)
on B200 (sm100). **Result: fusion loses ~0.45× across FIVE independent implementations,
including a faithful port of the FlashAttention-4 / CUTLASS-example-77 winning structure.
Root cause is now measured precisely: the op is L1TEX/TMEM-throughput-bound when fused, not
compute- or latency-bound. Decision: SHIP THE SPLIT.**

All perf = CUDA-graph-replay median, xn precomputed, µs. d=128 → (K,ND,D)=(128,512,128);
d=256 → (256,1024,256). All implementations CORRECT (cos 0.999997 vs fp32 torch, both d).

## Root cause (ncu, decisive — supersedes v1/v2 "latency/occupancy" hypotheses)

The single-warpgroup fused profiled at compute 14% / DRAM 1.3% / occupancy 9.25% / 1 CTA/SM,
75% short-scoreboard (TMEM) stall. v1/v2 blamed unhidden t2r latency at 1 CTA/SM. **The FMHA
ping-pong (impl #5) refutes that:** the 2nd transform warpgroup raised **occupancy 9.25%→15%**
(so warp count is NOT the cap — 1 CTA/SM ≠ the limiter) yet **compute stayed 14%** and
short-scoreboard rose to 77%. The bound is **L1TEX/MIO throughput = 67%** (the highest SoL
metric; compute 14%, DRAM 1.3%). Adding parallelism can't fix a throughput-saturated path.

The fused concentrates the transform's TMEM round-trip on ONE SM's L1TEX/MIO path: per ND
chunk it does t2r(a_acc) + t2r(b_acc) + r2t(h) + MMA-read(h). For this op the GEMMs are THIN
(K=128) so that transform traffic is comparable to / exceeds the GEMM compute → memory-path-bound.
- Bank conflicts are NOT the cause (split-expand has 8× more shared-store conflicts, runs 3× faster).
- No register spills (150–168 regs at BN=64, 0 local mem).
- deferred squeeze (#4) and K-deep expand lookahead both made it WORSE → it's epilogue/transform-
  bound, not expand-scheduling-bound.

## Why FlashAttention-4 wins on B200 but this op does not

FA4 / CUTLASS example 77 ship a Blackwell back-to-back GEMM (softmax as no-op) and hit 71%
utilization — same structural pattern (GEMM1 → elementwise transform → GEMM2, P fed to GEMM2's
A operand from TMEM). We ported that exact structure (impl #5: 2 softmax/silu warpgroups, ping-
pong over 2 tiles, P/h in TMEM via A-from-TMEM). It still loses **because attention is
compute-bound** (large Q@K, P@V dominate; the softmax TMEM traffic is small relative to the
GEMMs) whereas **this transition is transform-memory-bound** (thin K=128 GEMMs, full-size
elementwise SwiGLU → the transform's L1TEX/TMEM traffic is the bottleneck). The winning
condition for fusion (compute-bound so the transform hides under GEMM work) is absent here.

The split wins by **distributing** that same traffic across smem + HBM + cuBLAS and using many
SMs (cuBLAS squeeze runs ~2 waves), instead of concentrating it on one SM's L1TEX path at 1 CTA/SM.

## Blackwell / DSL techniques validated (reusable)

- **A-from-TMEM squeeze** (the true Blackwell analog of H100's register-source RS squeeze; there
  is no register-source MMA on Blackwell): `make_trivial_tiled_mma(..., a_leading_mode=
  tcgen05.OperandMajorMode.K, a_source=tcgen05.OperandSource.TMEM)`; place the A-operand TMEM
  tensor via `mma_s.make_fragment_A(cute.append(partition_shape_A((CTA_M,BN)), stages))` +
  `cute.make_tensor(cute.recast_ptr(tmem_ptr+off, dtype=bf16), tH_fake.layout)`; write h with
  `tcgen05.St32x32bOp(Repetition(8),Unpack.NONE)` + `tcgen05.make_tmem_copy` + a src fragment
  from the copy's own `partition_S(identity)` (retile of the t2r fragment aborts cross-family);
  `cute.arch.fence_view_async_tmem_store()` after r2t. Reference: cutlass
  `utils/mixed_input_helpers.py` (transform_partition / get_copy_atom_a_transform) and
  `examples/77_blackwell_fmha`.
- **FMHA ping-pong**: 2 transform warpgroups + 2 S/P/O TMEM buffers (S0@0, S1@128, P packed
  inside S region, O0@256, O1@384 = 512 cols; V aliases S). The 2 pipeline instances ARE the
  double-buffer. Raised our occupancy 9→15% (but didn't help, see above).
- **Deadlock gotcha (cost 1 subagent run):** in a ping-pong TMA producer the wab/ws emission order
  MUST match the MMA's consumption order. The MMA interleaves (expand 2 chunks ahead, then squeeze
  2 → needs ws early); emitting "all wab then all ws" deadlocks (MMA blocks on ws(chunk0) after
  expanding only chunks 0-3 while the TMA still owes wab 4-7 and won't emit ws until done). For the
  DEFERRED path (all expands then all squeezes) "all wab then all ws" is correct.
- **DSL gotcha:** never call `partition_D`/`make_tmem_copy` INSIDE an scf loop (tiled_copy becomes
  loop-carried → "failed to legalize" MLIR). Partition the full staged tensor OUTSIDE, index the
  stage inside. And host-time branches in `@cute.jit` must use `const_expr`/ternaries, not `if`
  (an `if` on `self.*` gets AST-transformed into a dynamic branch that tries to flatten `self`).

## TMEM budget note (512 cols)

Fused b2b needs a_acc + b_acc + o_acc + h co-resident. BN=64: single-stage d=128 = 288 cols,
d=256 = 416. 2-stage (pipelined) d=128 = 448; d=256 = 576 (overflows → d=256 stays single-tile).
FMHA ping-pong (2 tiles) fits d=128 in 512 by packing h inside the a_acc columns; d=256 needs
768 → ping-pong is d=128-only. o_acc (D cols) is permanently resident (squeeze accumulates across
all ND chunks) and is the biggest fixed consumer; it prevents 2 CTAs/SM (would need ≤256 cols each).

## Decision

**SHIP THE SPLIT** (`transition_b2b_sm100_ln` in `transition/cute/b2b_fwd_sm100.py`, wired into
inference + training). The fused is a correct, thoroughly-optimized research artifact; on B200 it
is L1TEX/TMEM-throughput-bound for this thin-GEMM + large-transform shape and does not beat the
split. Reopen only if the op shape changes toward compute-bound (larger K / d_hidden) or a lever
that reduces the transform's TMEM round-trip traffic appears.
