# triangle_attention — v7: dq grad stored bf16 (kills the last cast copy) — 1.78× vs baseline

**GPU:** H100 (sm90).  **Shape:** d_pair=512, L=384, n_head=4 → HEAD_DIM=128, B=1, bf16.
**Base:** v6 (fwd out in projection layout, 6.403 ms/layer).  **Baseline:** 10.98 ms.

## Verdict

**SHIP.** Store the query grad `dq` as **bf16** (was fp32) — matching dk/dv. Kills the backward
`copy_ [1,4,384,384,128]` (~0.13 ms, autograd casting the fp32 query grad down to bf16).
Correct (cos 0.99999 / 0.99998, unchanged), **step 6.403 → 6.165 ms (1.04× vs v6,
1.78× cumulative)**.

## Why dq was fp32 — a vestige of the atomic-add era

The original fused backward accumulated `dq` across query blocks with `atomic_add`, so it
needed an fp32 accumulator buffer (`dq = torch.zeros_like(q, dtype=torch.float32)`). The v2
FA2 split removed the atomics (dq is now fully written once by `_attn_bwd_dq`), switching
`zeros`→`empty`, but the **fp32 dtype was carried over by inheritance** — with no remaining
reason. `_attn_bwd_dq` accumulates `dq` in fp32 registers and stores once, exactly like
dk/dv; storing bf16 is precision-neutral (the cuBLAS/pytorch reference also stores bf16
grads). Confirmed by the cssb-server precision principle (session e54f858d): *bf16 in / fp32
accumulate / bf16 out* does not lower precision; explicit fp32 output/temps were byte-identical
to remove.

## Fix (one line)

`dq_proj = torch.empty(B, L, L, H*D, dtype=v.dtype)` (was `torch.float32`).

## Validation

`ta_verify.py` D=512 L=384 NH=4 bf16 vs pytorch fp32 ref: fwd cos 0.99999, grad_pair cos
0.99998, PASS. Precision unchanged.

## Copy attribution (ta_copyid) — all wasteful copies eliminated

- **Forward:** only `copy_ [1,4,384,384]` = `bias.contiguous()` (~0.0 ms, intentional — the
  gappy pair-bias load is the whole stride penalty; the copy is tiny).
- **Backward:** **no `aten::copy_` at all.** Remaining elementwise is `add_/add
  [1,384,384,512]` (pair-grad accumulation — pair feeds 5 projections, inherent autograd) +
  tiny weight-grad adds.
