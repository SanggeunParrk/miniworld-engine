# triangle_attention — v8: dbias row-reduction fusion via atomics — NO SHIP (1.2 ms loss)

**GPU:** H100 (sm90).  **Shape:** d_pair=512, L=384, n_head=4 → HEAD_DIM=128, B=1, bf16.
**Base:** v7 (6.165 ms/layer).  **Baseline:** 10.98 ms.

## Verdict

**DO NOT SHIP — revert to v7.** Fusing the dbias row-reduction (sum over the row index i)
into `_attn_bwd_dkdv` via `tl.atomic_add` is **correct but 1.2 ms slower** (6.165 → 7.372 ms).
The 384-way global-atomic contention costs far more than the reduce it eliminates.

## What was tried

v7 materializes a per-row dbias `[B,HL,L,L]` (~453 MB) in dkdv, then a separate `reduce(sum)`
kernel sums over the row index → `[B,H,L,L]`. Profiling put that reduce at **0.154 ms/step**
(2.6 %, reading 453 MB at ~2.9 TB/s — HBM-bound). v8 removed the intermediate + reduce: a
single shared fp32 `[B,H,L,L]` dbias, `atomic_add`-accumulated across the row index (a grid
dim) inside dkdv. Needed `reset_to_zero=["dbias_ptr"]` on the autotuner (else the ~8 config ×
N-rep tuning launches accumulate into the same buffer → grad cos 0.16).

## Why it loses — orthogonal reductions force the atomics

Correct (cos 0.99999 / 0.99998) but:

| kernel | v7 | v8 (atomic) |
|---|---|---|
| `_attn_bwd_dkdv` | 0.98 ms | **2.35 ms** (+1.37 ms) |
| `reduce_kernel` (dbias) | 0.154 ms | 0 (removed) |
| **step** | **6.165 ms** | **7.372 ms (+1.2 ms)** |

dbias reduces over the **row index i** (L=384), while dk/dv reduce over **query** (per row).
These are orthogonal, so in the per-row dkdv grid a program owns exactly one row's dsT tile
and cannot locally reduce dbias over rows — every one of the ~226 M dsT elements becomes a
global `atomic_add` with 384-way contention per `dbias[b,h,j,k]`. That converts 226 M cheap
coalesced stores (+ one 0.154 ms streaming reduce) into 226 M contended global atomics: dkdv
+1.37 ms, dwarfing the 0.154 ms saved.

A register/smem-local row reduction would need one program to iterate all rows for a fixed
(query-block, key-block) — but then dk/dv (which sum over query) go partial and need their own
atomics (moving, not removing, the problem). Not worth the rewrite for a ≤0.3 ms ceiling.

## Conclusion

v7's materialize + streaming reduce is near-optimal for this shape; the 0.154 ms reduce is
HBM-bound and cheaper than any atomic alternative. Keep v7 (6.165 ms, 1.78×). Analogous to the
B200 transition-b2b campaign: the "obvious" fusion loses; ship the split.
