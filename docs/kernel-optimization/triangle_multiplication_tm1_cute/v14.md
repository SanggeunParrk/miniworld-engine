# triangle_multiplication_tm1_cute — round v14 (feasibility: CUTLASS tuned Blackwell collective)

- Date: 2026-07-04
- Target kernel: tm1 gated GEMM `out = sigmoid(A@Bg.T) * (A@Bp.T)`, M-major → [B,D,L,L]
- Shape @ L=1024: M=L²=1048576, N=D=128, K=D=128. bf16 in / fp32 acc / bf16 out.
- Branch: `perf/tm1-cutlass-collective` off origin/main (2a10ee6, has stream fix).
- GPU: NVIDIA B200 (sm_100), CUDA 4.4.2 nvidia-cutlass-dsl, quack 0.3.11.

## Roofline (why the naive kernel is far from optimal)
- FLOPs (two GEMMs, proj+gate): 2·2·M·N·K = 6.87e10 = 68.7 GFLOP.
- Min traffic (A read + out write, gate not stored): ~536 MB. B200 HBM ≈ 8 TB/s → floor ≈ 0.067 ms.
- Naive kernel isolated GEMM = 0.63 ms ⇒ ~850 GB/s ≈ 10% HBM. Memory/latency-bound, huge headroom.
- Naive design: single-CTA, num_ab_stage=1, cluster(1,1,1), CtaGroup.ONE, simt (per-element) store,
  grid=[8192] tiny CTAs. No load↔MMA overlap, no acc double-buffer, slow simt C write.

## Prior negative result (hand-rolled persistence)
- v10/v11 hand-rolled a persistent + warp-specialized kernel → 1.89–2.07 ms (WORSE than naive).
- ncu of the hand-rolled persistent single-side plain GEMM: gpu_time 2.07 ms, sm_throughput 10%,
  dram 3%, long_scoreboard 122 inst — the hand-rolled mainloop stalls badly; simt store epilogue.
- Conclusion then: "naive persistence is not the lever". BUT that was hand-rolled, not the tuned collective.

## Verdict
The tuned collective does ONE side in ~0.093–0.10 ms vs the naive kernel's ~0.315 ms/side
(0.63 ms for two GEMMs) — **~3.4× faster per side**, and it saturates ~72% HBM. The naive
mainloop, not sm_100, was the problem. Fusing the gated dual-B into one kernel reads A once and
writes out once (~536 MB — same traffic as ONE plain GEMM), so the whole gated side should land
near one-GEMM time (~0.10 ms). Hypothesis validated → v15 builds the gated kernel on this collective.
