## Step 1 — run v6 on B200 as-is; identify the sm90-only piece (probe)
| v6 component | backend | sm100 status |
|---|---|---|
| LN_in `triton_layernorm` | Triton | works (arch-agnostic) |
| **front `trimul_inproj_cute_forward(bdll_direct=True, return_preact=True)`** | quack gated-GLU, M-major postact TMA store | **BROKEN** — left/right cos 0.054, 0.052 |
| contraction fwd/bwd `torch.bmm` | cuBLAS | works |
| LN_out+@Wp `_te_forward/_te_backward` | cuBLAS + Triton ("no quack/SM90 dep") | works; `d_view` m-major → `d_tri=d_view.t().reshape(D,L,L)` **contiguous (free view)** |
| gate `gate_elem_triton/gate_elem_bwd_ew` | Triton | works |
| front bwd+dW `front_bwd_dW` | Triton + cuBLAS | works |
| dxn `torch.mm`+`addmm_` | cuBLAS | works |

Only the front is sm90-only. Root cause (already documented in `front_sm100.py` + memory
`trimul-sm100-front-fused-win`): quack's sm_100 **gated-GLU** epilogue stores the postact through a
StMatrix m-major atom delivering a fixed 32-channel/thread tile that the GLU N-halving cannot
compose with → the M-major (bdll) store SILENTLY HALF-WRITES each tile. This is specific to the
GATED epilogue.

## Step 2 — sm100 front (`front_train_sm100.py`), layout contract unchanged
Key insight (= the round-plan's point): the bdll-direct store is a **reduction-free pure GEMM
store**, so its layout is free (unlike the dgrad LN-bwd epilogue whose reduction axis is coupled to
the store, cos 0.982). quack's **non-gated** m-major store IS bit-correct on sm_100 (verified:
preact cos 0.999999, left/right cos 0.999997 @ L=128..1024). So the sm100 front =
1. ONE non-gated m-major GEMM `x @ b_lr -> preact[4D,L,L]` (bdll, written straight through an
   M-major view — no permute), then
2. a Triton GLU pass `left/right[d] = sigmoid(preact[gate_d])*preact[proj_d] -> [2D,L,L]` (bdll).

Same DATA as the sm90 gated launch (preact + postact), same layout contract, **0 transposes**. GLU
as a separate elementwise pass instead of a fused epilogue = implementation detail, not an
algorithm/precision change.

## Step 3 — `v6_training_merged_sm100.py` (`V6TriMulMergedSm100`)

## Core trade-off answer
The round plan asked whether v6's torch.bmm-based structure loses the tcgen05 advantage. It does
NOT: removing v11's two (M,D) physical transposes (front blld→bdll + d_tri LLD→DLL, ~0.24 ms/iter
of near-peak-BW traffic) plus v11's extra fused-kernel/relayout overhead more than compensates for
staying on cuBLAS bmm. The faithful H100 v6 structure is genuinely the better one on B200.
