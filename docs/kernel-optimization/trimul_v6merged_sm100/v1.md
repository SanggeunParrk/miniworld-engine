# trimul v6-merged sm100 (B200) TRAINING — v1: memoize the front-GEMM occupancy probe

**Target:** `V6TriMulMergedSm100` / `BidirV6TriMulSm100` (sm100 single-dir + bidirectional
trimul TRAINING fwd+bwd), the current fastest trimul training path. New optimization track on
the v6-merged design (the `trimul_train_b200` v1–v15 track is the older train_b200 lineage).

**GPU / env:** NVIDIA B200 (sm100), pixi default env, GPU2. bf16 in / fp32 acc / bf16 out,
B=1, d_pair = d_hidden = 128. `QUACK_CACHE_ENABLED=0`, `MINIWORLD_TRANSITION_CUDA_B2B=0`.
Isolated git worktree `~/psk/mwk-trimul-v7` (branch `perf/trimul-v7-opt` off origin/main) so the
concurrent transition-sm100 session's checkout is untouched.

**Bench:** `bench_trimul_train.py` — standalone trimul(out) and bidir, TRAINING (fwd + bwd with
a **dense** grad_output), ours (CUTE) vs cuequivariance, same weights, L ∈ {256,384,512,1024}.
**Validation:** `verify_train.py` — fwd output + input-grad cosine vs the PyTorch reference.

## Baseline observation

Ours training latency was **~38 ms FLAT for every L** (256 → 1024), while cuequiv ran 1.2–14 ms.
A latency independent of problem size is a per-call *host/launch* overhead, not compute:

```
=== trimul(out) TRAINING (fwd+bwd) — BEFORE ===
     L    ours ms   cuequiv ms   speedup
   256     38.09        1.33        0.03x
   512     38.13        1.92        0.05x
  1024     38.53        6.96        0.18x
```

## Bottleneck theory

This is the exact bug already fixed on the **inference** path (branch `perf/inf-occupancy-memoize`,
commit dc61469 "memoize occupancy probe"): the CUTLASS-DSL occupancy probe
`cutlass.utils.HardwareInfo().get_max_active_clusters(1)` **JIT-recompiles a probe kernel on every
call**. It was memoized in the inference kernels (`sm100_gate_gemm_collective.py`,
`ln_linear_sm100.py`) but the **training front GEMM** `front_fused_gemm_sm100.py` still called the
un-memoized `HardwareInfo()` probe at **both** `fused_front_gemm` (L625) and `fused_front_gemm_sig`
(L665). The sig path runs once per forward → one probe recompile per training step → the flat
~38 ms. Every other sm100 kernel in the path already uses quack's `@lru_cache`-wrapped
`get_max_active_clusters` (device-constant on cluster size).

## Change (one focused fix)

`front_fused_gemm_sm100.py`: `import get_max_active_clusters from quack.cute_dsl_utils` and replace
both `utils.HardwareInfo().get_max_active_clusters(1)` call sites with the memoized `get_max_active_clusters(1)`.
3 lines. **No kernel/numeric change** — the occupancy value is device-constant; only the redundant
per-call recompile is removed.

## Results

```
=== trimul(out) TRAINING (fwd+bwd) — AFTER ===
     L    ours ms   cuequiv ms   speedup
   256      1.004        1.293      1.29x
   384      1.011        1.299      1.28x
   512      1.027        1.920      1.87x
  1024      3.577        6.965      1.95x

=== bidir TRAINING (fwd+bwd) — AFTER ===
     L    ours ms   cuequiv ms   speedup
   256      1.059        2.720      2.57x
   384      1.079        2.737      2.54x
   512      1.563        4.006      2.56x
  1024      6.071       14.230      2.34x
```

- **~10–38× faster** than the probe-bound baseline; ours is now compute-bound and scales with L.
- Beats cuequivariance **1.28–1.95×** (single-dir) and **2.34–2.57×** (bidir) — matches the
  design's known peak, previously entirely masked by the launch overhead.

## Notes / next

- A separate robustness gap surfaced while building the bench: the merged backward passes the raw
  incoming grad straight into the Triton `gate_elem_bwd_ew` / front-bwd kernels, which assume a
  contiguous `(M,N)` layout. A `y.sum().backward()` (or any upstream op producing a **stride-0
  expanded** grad_output) makes those kernels read a 1-element storage as if it were `M·N` → IMA.
  Real training feeds a dense grad, so it never triggers there; a defensive `.contiguous()` on the
  incoming grad would harden it. Deferred (tracked separately from this perf round).
- **Next round:** with the launch overhead gone, profile the true compute bottleneck (nsys/ncu):
  front bwd `_dconcat_sig` + `dispatch.mm`, the bmm contractions, and the te LN_out+@Wp.
