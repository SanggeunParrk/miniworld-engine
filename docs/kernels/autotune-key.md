# 오토튠 키 규약

한 커널의 튜닝 결과는 **어떤 키로 캐시에 들어가느냐**로만 재사용된다. 키가 너무 거칠면 서로 다른
형상이 한 config를 공유하고, 너무 잘면 빌드가 방문하지 않은 형상마다 캐시 미스가 난다. 이 문서는
그 키의 정의다. 구현은 [`autotune/shape_key.py`](../../src/miniworld_engine/autotune/shape_key.py).

## 두 축

    dim     64  128  256  384  512  768          채널 폭. 정확 집합
    shape   커널의 level에 따라 (아래)            토큰/원자 개수 L

`level`은 [`kernels/registry.csv`](../../src/miniworld_engine/kernels/registry.csv)의 열이고
개발자가 직접 채운다 ([naming.md](naming.md)의 등록 규칙 참조).

    token   128  256  384  512
    atom    256  512  1024  2048  4096  8192
    both    합집합: 128 256 384 512 1024 2048 4096 8192

## 매핑

shape는 **내림 + 양끝 클램프**다.

    최소 미만  -> 최소        token 64    -> 128
    최대 초과  -> 최대        atom  99999 -> 8192
    중간의 값  -> 이하 최대   token 192   -> 128

내림인 이유: 128에서 튜닝한 config에게 192 폭을 시키면 타일을 더 돌면 되지만, 256에서 튜닝한
config에게 192를 시키면 그 config가 본 적 없는 타일 수다. 내림은 튜닝된 config를 작업량의
하한으로 유지한다.

`dim`은 클램프하지 않고 **거부한다**. 폭은 커널이 빌드된 폭이고, 집합 밖의 값은 "아무도 튜닝하지
않은 폭으로 돌고 있다"는 뜻이다. 이웃 버킷으로 조용히 접으면 그 사실이 숨는다.

버킷은 인덱스가 아니라 **값**을 반환한다. 캐시 키와 `axes.csv`에 그대로 들어가는데 `384`는 의미를
말하고 `2`는 말하지 않는다.

## shape는 L이다, M이 아니다

**shape는 토큰 또는 원자의 개수 L이고, 커널이 받는 행 수가 아니다.** `L*L`행을 도는 pair 커널과
`L`행을 도는 선형 커널은 같은 L에서 같은 형상이고 같은 버킷 공간을 써야 한다.

    length_of(shape) == shape[-2]      평탄화 "전" 활성값에서 읽는다

채널 축이 항상 마지막이므로 한 규칙이 두 레이아웃을 덮는다 — pair `(B, L, L, D)`와
token `(B, L, D)` 둘 다 거기 L을 둔다. 제곱근도 분기도 없다.

**반드시 launcher에서 읽어야 한다.** 텐서가 `(M, D)`가 되고 나면 정보가 사라진다. `M`만으로는
선형 `M=384`와 `L=20`에서 온 pair `M=384`를 구분할 수 없다. 평탄화된 행렬만 받는 내부 launcher는
계산할 수 없으므로, **아직 형상을 아는 호출자가 키를 계산해 내려보낸다.** `isqrt(M)`으로 역산하지
않는다 — 그건 어느 레이아웃이 M을 만들었는지에 대한 추측이다.

이전에는 기준량 셋(L, M, 평탄 원소 수)이 edge 집합 셋에 각각 붙어 있었다. 각 호출부는 자기 집합과
일관됐지만 같은 물리적 L이 계열마다 다른 버킷 공간에 떨어졌고, 평탄 원소 수를 쓰던 6곳은 이미 완전히
붕괴해 있었다 — D=128에서 L=64부터 512까지 전부 같은 인덱스, 즉 모든 시퀀스 길이가 튜닝 config
하나를 공유했다.

## `shape_key`와 `GROUP_M`은 다른 것이다

| | `shape_key` | `GROUP_M` |
|---|---|---|
| 무엇 | 캐시 라벨 | L2 swizzle 그룹, 타일 knob |
| 출처 | `token_key`/`atom_key`/`both_key` | config CSV |
| 커널 본문 | **읽지 않는다** | 읽는다 |
| `key=[...]` | 올라간다 | 안 올라간다 |
| 개수 | 90 | 4 |

이름이 같으면 파라미터를 봐도 어느 쪽인지 알 수 없다. `GROUP_M`을 읽는 커널은 넷뿐이다 —
`adaln/triton/fused3.py::_gemm_gate_kernel`, 그리고 `conditioned_transition/triton/train_fused.py`의
`_dgemm_kernel` / `_dh_gatebwd_kernel` / `_dx_swiglubwd_kernel`.

## 강제

`tests/test_registry_complete.py`가 검사한다. GPU 불필요.

* **모든 launch 키워드가 대상 커널의 파라미터인지.** 이게 없어서 실제로 깨졌다: 90개
  파라미터를 `shape_key`로 rename할 때 커널을 정의하지 않는 파일이 건너뛰어져, 14곳이 옛 키워드를
  계속 넘겼다. Triton은 모르는 키워드를 삼킨 뒤 필수 인자가 없다고 죽으므로 에러 메시지가 원인이 된
  낡은 키워드가 아니라 **없는 파라미터**를 가리킨다. 그래서 push된 커밋까지 갔다.

키가 틀려도 **수치는 그대로 통과한다** — 캐시 라벨이니까. 정확도 스윕으로는 잡히지 않는다. 새
launcher를 붙였으면 대표 형상 두어 개의 키를 위 표와 **손으로** 대조해야 한다. 특히 모든 형상이 한
버킷으로 붕괴하는 경우가 스윕에 초록으로 보인다.
