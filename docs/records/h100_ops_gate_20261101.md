# H100 / B200: no Triton through the `ops.*` facades, the bias-only DiT fallbacks and the AugmentedAttention helpers (2026-11-01)

Branch `fix/h100-ops-gate` (from main 5d7786e40, merged with main d0dea0ea9). Decision (user): H100 / B200 never run portable Triton; the existing hand-CUDA kernel serves a facade where one exists for the op / shape / dtype, else the
PyTorch form; no Triton on H100 / B200, no code dropped (the Triton versions stay as `_*_triton`). The first version of this branch routed the facades that lost their Triton kernel to plain PyTorch statements; the measurement of that
routing ([h100_ops_gate_perf_20261101.md](h100_ops_gate_perf_20261101.md)) showed 3 - 12x slowdowns and an out-of-memory at L = 1024, so the facades are now wired to the CUDA kernels that already serve the same ops
(`kernels/_h100_ops.py`, below). No new kernel was written.

## Call paths found (static search + the gate tests)

The wrappers (`kernels/_h100_ops.py`) answer None when no CUDA kernel serves the call (another card: B200 keeps the PyTorch statements; a dtype, width or layout outside the kernel's contract; a CPU tensor; a `torch.compile` trace), and
the facade then runs the PyTorch form. The registry dtypes were checked first: the triangle-attention core and TriMul are bf16 rows only, so fp32 never reaches them.

Already gated (read, not changed): `modules/*` forward paths (`restricted_card` / `portable_leg_allowed`), `SWAAtomBlock` / `SwiGLUFFN`, `SWA3DRoPEAttention`,
`ops.transition`. Not changed, still Triton-bearing but not reached by the recorder runs below: `integrations/opm_train.py` (`_opm_prologue_kernel`, legacy,
`_CUDA_PROLOGUE_FOR_LEGACY`) and `integrations/pwa_train.py` (`_pair_fwd_kernel` / `_pair_bwd_kernel`, `pwa_wide` replaces them); the B200 branch of
`integrations/token_dit.py` (non-(9, 0) cards use `FusedTokenDiTComposed`, which "degrades to the Triton hooks"): not run here (no B200).

## Finding: the previous Triton triangle-attention core is wrong for QK-normed q / k with a strided v

Probe (job 41353, bf16, L64, 4 x 32): `triton_triangle_attention_pair_bias(q, k, v, bias)` with contiguous q, k (what the QK norm returns) and v a strided
`rearrange` view returns an output with relative error 1.41 against fp32 (uncorrelated); the same call with v contiguous: 2.1e-3; all-strided (no QK norm): fine. So
`ops.triangle_attention(..., norm_*_weight=...)` on the portable path (any card with a record, and H100 under the A/B switch) returned wrong values; the
new paths agree with fp32 (bf16 outputs 4e-3). `modules.TriangleAttention` with `use_qk_norm` on a portable card has the same input layout. Not fixed here (a Triton kernel change moves its caches).
`test_ops_no_triton_gpu.py` reports it and does not compare against the previous output for that case (fp32 yardstick instead).

## Performance

Measured: [h100_ops_gate_perf_20261101.md](h100_ops_gate_perf_20261101.md) (342 rows, before / after the CUDA wiring, the slowdown list with causes). In short: 208 of 342 rows were > 5% slower with the PyTorch routing (86 of them > 2x), 107 are now (6 > 2x:
fp32 `augmented_attention_pair_bias` and bf16 8 x 64 at L1024, which have no CUDA core); TriMul and triangle attention are at or below the Triton path (the sm_90 triangle core is 0.7x at L1024); `ops.triangle_attention` at L = 1024 no longer runs out of memory.
