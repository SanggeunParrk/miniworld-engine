# B200-style TriMul port to H100 — 2026-10-07

Implemented as an explicit candidate in `h100_b200style.py`, connected to the existing modules through `MINIWORLD_TRIMUL_H100_B200STYLE=1`. The default selector is off. This is an algorithm port using Hopper TMA/WGMMA, not a Blackwell binary or an assertion that the same fusion is faster on H100. D64/D128 already use the analogous high-level K1/K3/B1/B7 structure; this change addresses the different wide-D path.

## Algorithm and activation lifetime

* Forward K1 combines input LayerNorm, four input projections, sigmoid, mask, and plane production; it saves input mean/rstd, not normalized input rows or front preactivations.
* Contraction uses the existing B200 architecture-independent `torch.bmm` formulas: two products for bidirectional, one for single direction.
* Both LayerNorm affines are folded into output/gate weights. Hopper K3 streams raw contraction/input operands, combines both projections, output LayerNorm statistics, gate, row dropout and residual. Training additionally saves rounded projection/gate values and output mean/rstd; inference skips those allocations.
* Backward uses B200's folded-weight derivative identities. It recomputes front preactivations with Hopper WGMMA and directly generates packed gate/projection gradients. A SW128 shared tile and TMA stores produce token-major gradients for the combined input/weight GEMMs. The auxiliary device math is taken directly from B200 `wide_aux.cu` and `wide_bwd.cu` through driver-native wrappers. The original runtime binding remains private diagnostic code and is not the dispatched implementation.
* Saved tensors are gated planes, contraction, input/output statistics, folding vectors, projection and gate values. Forward saves neither `norm`, `xn` nor `pre`. Backward materializes `dpl`, packed `dcat`, and recomputed `xn`; reduced saved state does not imply reduced total execution time or HBM traffic.

The Hopper packed projection block is 32 channels, whereas the B200 source uses 64. Kernel tiles, producer/consumer scheduling, and TMA barriers are adapted to Hopper. Like B200 K1WB, the port stages contraction gradients with TMA before producing token-major gradients for TMA stores. Hopper consumes shared gradients with scalar fragment reads rather than B200's TMEM/ldmatrix layout. One 8 KB stage per warpgroup is reused for input then output, with barriers around that lifetime transition. Fusion, recomputation and staged transfers follow B200; architecture-specific instructions and register layouts differ.

## Serving contract and use

The opt-in path serves H100, B=1, contiguous BF16 pairs, D256/384/512, L128/256/384/512/640/768, hidden=D per direction and eps=1e-5. It accepts outgoing, incoming and bidirectional operations. Matrix parameters may be BF16 or FP32 masters; normalization parameters are contiguous FP32. Row dropout scale has shape [L,D] and BF16 dtype. Compact residue masks and full pair masks are accepted; the direct entry point also accepts an empty mask. Existing backend policy and supported training-width settings still apply.

```bash
MINIWORLD_TRIMUL_H100_B200STYLE=1 <existing training or inference command>
```

An unsupported module shape continues through the existing selection. Calling the explicit kernel with an unsupported contract raises `ValueError`. No default dispatch, release installation, canonical completion mark, commit or push is changed by this experiment.

## Correctness and safety

Slurm job 27423 on the frozen final source: **49 tests passed**, including full-module dispatch and all input/parameter gradients, BF16 matrices and FP32 masters, all three directions, D256/384/512, L128/384/768, mask/dropout, zero masks, inference/training equality and changed-input CUDA Graph replay. Numerical checks use an independent FP32 formula, nonzero random weights, nonidentity norm affines, nonzero upstream gradients, and relative Frobenius thresholds output <0.006 / every gradient <0.01. The graph tests change inputs, weights, masks, dropout scale and upstream gradients across replays and warm up on the capture stream.

Frozen final source, Slurm job 27420:

| Tool | Coverage | Result |
|---|---|---|
| memcheck | 25 gradient, graph and zero-mask tests | 0 errors |
| racecheck | all three width configurations, bidirectional F+B, changed graph replay at D256/D512 (5 safety scenarios) | 0 hazards/errors |
| synccheck | 25 gradient, graph and zero-mask tests | 0 errors |

There is no CUDA kernel-name filter or sanitizer-error suppression. Racecheck's five safety scenarios check finite outputs/all gradients and actual changed-input graph execution; independent FP32 numerical comparisons are performed by the 49-test suite and memcheck/synccheck rather than running a second oracle model under race instrumentation. Sanitizer coverage is L128; wide L384/L768 numerical and module timing coverage is separate. FP32-master timing, B>1, exhaustive config search, and SOL90 are not claimed.

The initial runtime auxiliary binding passed numerics but reported a CUDA API invalid-handle error under memcheck. It was replaced with driver-native wrappers rather than suppressing the error. The initial scattered-gradient version was also slower; timings below use the final TMA-store version only.

## Paired full-module performance

Frozen `snapshot-v4`, Slurm job 27421, NVIDIA H100 80GB HBM3, driver 575.51.03. Each cell's baseline and candidate use the same allocated GPU; UUIDs are retained in the job logs and run metadata. BF16 activations/matrix parameters, FP32 norm affines, B1, one residual-inclusive layer, mask probability 0.1. Inference dropout=0, training dropout=0.25; training includes full forward and every input/parameter backward with fresh gradients, excludes optimizer. The harness's `bf16-mixed` label pins these TriMul matrix parameters to BF16 and does not describe FP32-master timings. Compilation is requested and manual CUDA Graph replay is measured.

Every baseline/candidate capture goes through the unchanged shared `benchmarks/runners/bench.py` (`main`, `measured_result`, `bench_time`). Seeded tensors are checked equal. After ten paired warmups, 90 alternating AB/BA CUDA-event pairs measure the same captured complete steps. One fresh process per mode/direction/width bounds compiler recompilation state. Separately labeled eager profiles establish the actual K1/K3/K1WB dispatch and explain stage costs; they are not the final timing. Source and run hashes, compile/graph evidence and raw samples are retained in the artifacts.

**Speedup = current default time / B200-style time.** Above 1 favors the candidate. This is a matched comparison with the current project default, not a new matched run against every external kernel. The earlier [external comparison](trimul_comparison_h100_20261007.md) used different mask/timing conditions and its numbers should not be combined into precise candidate-versus-vendor ratios.

The candidate is slower in all 24 measured cells, so it does not qualify as a faster default and the selector remains off. The final eager profiles show outgoing D512/L768 K1WB at 5.80 ms versus 3.85 ms for forward K1; bidirectional K1WB at 11.55 ms versus 7.70 ms for forward K1. These separately labeled profiles diagnose this implementation, not an inherent limit of B200's fusion algorithm on H100. Front recomputation and separate contraction-gradient GEMMs still distinguish this path from the optimized H100 baseline. The explicit candidate remains available for subsequent architecture-specific work.
