# H100 TriMul at large L vs the Anthropic kit (single direction, D128 / D256 / D384), 2026-10-30

Question: in FoldForge's Protenix-v2 5I28 x12 trunk (1536 tokens, d_pair 256) TriMul took 6.78 ms/call on the engine and
6.33 ms/call with `backend: anthropic` (module CUDA events, 2026-10-29). Is the engine slower than Anthropic's `trimul_native` v5
at large L, and why?

Answer: no. The 6.33 ms was a measurement artefact of the whole-model `backend: anthropic` run (below). With identical
surroundings the engine's TriMul is 2.5 % faster in the model and 1-5 % faster standalone at every L for D256. The one real gap
was D384 beyond L1024 (up to 3 % slower than Anthropic), fixed by routing it to the B200-style port (now 15-17 % faster).

Setup: H100 80GB HBM3 (node01), torch 2.13 + cu129, branch `perf/trimul-bigl` from main 41345e19. Anthropic = the unmodified
`trimul_native` v5 1.2.2 sources rebuilt with nvcc 12.9 (`TRIMUL_NATIVE_BUILD_DIR=~/ext/trimul_native_cu129/build`, served through
`integrations.anthropic_trimul.update_unidirectional`, i.e. `face.serve`, the "fast" class; the kit's own copy has the same
sources and VERSION). Both rows run in ONE process on the same weights and input (bf16 matrices, fp32 LayerNorms, all-true
token mask unless noted), outputs bitwise equal (max |diff| 0.0 in every cell). Times: CUDA-graph replays, alternating order,
median of 9; "hot" = each call preceded by six 8192^3 bf16 GEMMs (sustained load), events around the TriMul call only.
Scripts: `~/miniworld-engine-scratch/perf1030/probe/` (`trimul_probe.py`, `kern_probe.py`, `cpu_probe.py`, `train_probe.py`),
FoldForge runs `~/miniworld-engine-scratch/perf1030/ff/` (`ff3.sh`, `ff4.sh`).

## 1. FoldForge, Protenix-v2 5I28 x12 (1536 tokens), `_TriangleMultiplication` CUDA-event time per call

400 calls per trunk (384 trunk c256 + 16 template c64), 3 warm repeats, one job on one GPU, runs in sequence.

| run | engine | TriMul backend | other modules | trunk (s) | TriMul ms/call (3 warm) |
|---|---|---|---|---|---|
| ff_main | main | engine | engine | 13.70-13.76 | 6.874 / 6.903 / 6.908 |
| ffa | main | anthropic | `backend: anthropic` (TriAttn etc. on the PyTorch reference) | 25.53-25.63 | 6.386 / 6.410 / 6.410 |
| ff_branch | this branch | engine | engine | 13.71-13.73 | 6.870 / 6.881 / 6.890 |
| ffx_anth | main | anthropic (`engine.ops: {trimul: anthropic}`) | engine | 13.70-13.79 | 7.042 / 7.061 / 7.085 |
| ff_main2 | main | engine | engine | 13.67-13.75 | 6.867 / 6.889 / 6.901 |
| ffx_anth2 | main | anthropic (`engine.ops`) | engine | 13.73-13.81 | 7.054 / 7.087 / 7.091 |

The 2026-10-29 gap (6.78 vs 6.33) reproduces as ff_main vs ffa. It disappears, and reverses, when only TriMul changes backend
(ffx_anth vs ff_main: Anthropic 2.5 % slower). The whole-model `backend: anthropic` run sends triangle attention, LayerNorm and
the linears to the PyTorch reference (trunk 25.6 s instead of 13.7 s): the card runs cooler and TriMul's kernels run at higher
clocks. The H100 here is power-bound under these kernels (the contraction GEMM runs at ~370 TFLOP/s), so a module's time
depends on what runs around it; compare backends per op, not whole-model backends.

## 3. Host cost per eager call (D256, mask)

`_run_inference` built a fresh plan cache per call, so every call re-encoded 11 TMA descriptors and both argument packs. Now
`h100_inference._Kernels.plans(w)` keeps one plan cache per weight set (LRU, 256 sets).

| | dispatch while the GPU is busy (ms) | before | after | Anthropic |
|---|---|---|---|---|
| D256 L1536 | out / in | 0.534 / 0.518 | 0.316 / 0.318 | 0.288-0.307 |
| D256 L64 | out / in | 0.507 / 0.510 | 0.300 / 0.304 | 0.266-0.292 |
| D384 L1536 (port) | out / in | - | 0.377 / 0.366 | 0.296-0.306 |

GPU time is unchanged (graphs). It matters in eager callers whose queue drains (FoldForge runs the trunk eagerly above
`trunk_graph_max_tokens` 512); at L1536 the queue stays full, so ff_branch equals ff_main above.

## Left

- D384 at L > 1024 with L % 128 != 0 still runs tmn (about Anthropic's speed): padding to the port's 128-token tiles costs two
  extra pair-sized copies (~2 ms at L1500), more than the port saves there.
- D256: tmn and the port tie (1 %) at L >= 768; both are bounded by the power-limited contraction GEMM (~40 % of the call).
