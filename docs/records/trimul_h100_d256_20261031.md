# H100 TriMul D256 (one direction, inference) vs Anthropic `trimul_native`, 2026-10-31

Branch `perf/trimul-d256` (from `perf/trimul-15pct`). Setup, probes and conventions as `trimul_h100_vs_anthropic_15pct_20261030.md`
(graph replays, alternating, median of 9 or 11; ours / Anthropic < 1 = ours faster; outputs compared bitwise with Anthropic's).
Probes: `~/miniworld-engine-scratch/perf1030/probe/` (`k3_diag_probe.py`, `k3_split_probe.py`, `lt_probe.py`, `lt_fixed_probe.py`,
`grid_probe.py`).

## 1. K3: where the time goes (port K3, D256, ROWPAD maps, graph)

`K3_DIAG` measurement builds: 1 = no epilogue arithmetic (y = the x tile as loaded), 2 = no MMAs issued.

| L | full | no epilogue | no MMA | neither | HBM floor (3.6 bytes x L^2 D / 2.6-2.8 TB/s) |
|---|---|---|---|---|---|
| 512 | 0.188 | 0.152 | 0.170 | 0.152 | 0.145-0.155 |
| 1536 | 1.597 | 1.311 | 1.443 | 1.310 | 1.29-1.39 |

Without its epilogue arithmetic K3 streams at the HBM rate; the epilogue costs ~19 % because HBM idles while it runs (the MMAs
hide under the streams). Variants that made TMA zero-fill instead of reading (pair-row extent 1) turned out slower than the real
loads at L1536, so the earlier "83-86 % non-memory" reading (previous record, section 4) overstated K3's compute share.

Rejected: **split operand rings** (k3.cu `NSA` / `NSB`: x / tri chunks in their own deeper ring, weights in a 2-stage ring, one
producer thread each, so the DRAM prefetch can run ahead through the epilogue): 20-50 % slower at D256 / D384 L256-2048 (D256
L512 0.231 vs 0.191, L1536 1.97-2.04 vs 1.65): with two weight stages the L2 latency of each 32 KB weight chunk shows; three
weight stages next to a deeper A ring exceed shared memory (239 KB). Outputs bitwise equal.

## 2. The contraction: cuBLASLt configurations

cuBLAS's default pick (torch.bmm; the engine's zero-workspace `bmm` picks the same kernels) is not the fastest configuration of its
own kernel family at TriMul lengths. Enumerating `cublasLtMatmulAlgoGetHeuristic` candidates (algorithm 66, one k-pass, bitwise
equal outputs) and timing them (graph, alternating; D256 = 256 planes per launch):

| L | out: best / default | in: best / default |
|---|---|---|
| 256 | t20c1k3 0.945 / 0.941 | t20c1k3 0.943 / 0.939 |
| 384 | none faster (t20c3k2 1.06-1.07) | none |
| 512 | t20c1k3 0.905 / 0.913 | t20c1k3 0.922 / 0.920 |
| 640 | t29c3k5 0.851 / 0.831 | t29c3k5 0.862 / 0.857 |
| 768 | t20c1k3 0.885 / 0.883 | t20c1k3 0.817 / 0.814 |
| 896 | t20c3k2 1.02 / 0.93 | t29c3k5 0.876 / 0.881 |
| 1024 | t20c1k3 0.886 / 0.859 | t20c1k3 0.881 / 0.861 |
| 1152 / 1408 / 1664 | no candidate | no candidate |
| 1280 | t29c1k3 0.888 / 0.885 | t29c1k3 1.09 / 0.94 (not kept) |
| 1536 | t201c2k5 0.954 / 0.937 | 0.97-1.10 (not kept) |
| 1792 / 1920 / 2048 / 2304 | 0.93-0.98, not reproduced | 0.98-1.0 |
| 2560 | t29c1k3 0.936 / 0.942 | 0.98-1.01 |

(tNcMkK = tile id N, custom option M, cluster shape id K; two values = two processes.) Which configuration wins, and whether the
heuristic offers it, changes from length to length (at L896-1408 the L768 winner runs 1.0-1.4x), so a fixed tile-shape rule does
not work and a runtime timing pass would make dispatch depend on timing noise. `_h100_bmm.LT_CONFIGS` lists the entries above that
reproduced at <= 0.95 in two processes, keyed (L, a transposed, planes per launch); `_h100_bmm.contract` takes the heuristic
candidate with that configuration (no workspace) and falls back to `bmm` elsewhere. Used by the packaged K1/K3 path and the port's
one-direction contraction (B200's `b200_infer._contract` unchanged). `cublasLtMatmulAlgoInit` with the same attributes is refused by
`cublasLtMatmulAlgoCheck` for most of them, so the heuristic's own candidate is taken.
