## What was built

No fp32 path existed on H100 (the engine has no portable fallback there), so fp32 ran the PyTorch statements. The new path (`kernels/trimul_inproj/cuda/h100_f32.py`, sources in `h100_f32_sources/`,
dispatch `integrations/trimul_h100_f32.py`) follows the bf16 structure with TF32 wgmma kernels around two cuBLAS contractions; stages, shapes, kernel times and accuracy are in
[docs/gpus/h100/trimul/trimul.md](../gpus/h100/trimul/trimul.md#fp32-activations-on-tf32-tensor-cores--bidirectional-d128-2026-10-27).

Design points that decided the numbers (H100, kernel time of one call from the profiler, L768):

| decision | measured |
|---|---|
| planes channel-major `[512][T]`, written by the front GEMM epilogue, read by cuBLAS with no copy (NT / TN batched TF32 at 260-310 TFLOP/s) | contractions 0.9 ms of 2.82 ms inference |
| front: one persistent TMA + wgmma kernel, 128 tokens x (128 gate + 128 projection rows) per unit, m64n256k8 | 0.71 ms for 155 GFLOP (217 TFLOP/s) |
| back: LN_out + transpose kernel, then a two-accumulator wgmma kernel with the residual in the epilogue | 0.48 + 0.54 ms (memory-bound: 1.2 GB + 1.5 GB) |
| training: do not save the gate pre-activations; recompute them in the backward GEMM (`front_bwd_kernel`) | saving them cost 1.3 ms in the forward and a 2.1 ms elementwise pass in the backward; recompute 1.64 ms in total |
| LN_out backward with the channels as the GEMM's M dimension, `s1 / s2` from 128-term dot products against `Wo w` and `proj - Wo b` | no cross-channel reduction in the GEMM; 0.81 ms, dgamma / dbeta in registers |
| no atomics anywhere (per-block dgamma / dbeta partials summed in fixed order) | y and all 11 gradients bitwise run to run |

Kernel time of one call (profiler, includes the probe's input clones in training): inference 0.686 / 2.823 ms, forward + backward 2.87 / 11.07 ms (L384 / L768).

## Is the portable rung fair?

Speed: portable inference is 1.8 - 3.4x faster than PyTorch, so the rung is real, not a slow strawman. Accuracy (module with the same weights, vs fp64, relative to PyTorch TF32): output 1.11x, gradients
1.50x (x), 1.54x (`ln_pair.bias`), 1.54x / 1.53x (`to_left`, `to_right` weights), 1.29x (`ln_pair.weight`), the others 1.00 - 1.16x (L384, mask on; L64 identical). So the portable
rung sits at / slightly above the 1.5x convention on four gradients while the CUDA path is at 1.00 - 1.07x; the CUDA / portable ratio is not flattered by the portable rung being
sloppier than the CUDA one in the speed direction, but the portable rung is the less accurate of the two.
