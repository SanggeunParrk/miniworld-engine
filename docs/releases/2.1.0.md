# v2.1.0: CUDA-first tuning and bounded Triton defaults

Status: source implementation with CPU validation; GPU qualification pending. No new GPU timing, CUDA Graph or
sanitizer qualification is claimed for this release's new tuning integrations.

## Build policy

The default build follows actual module dispatch on the target GPU. A supported
CUDA route is tuned there; the builder no longer forces an unused Triton
alternative just to fill a cache. Triton operations that still execute inside a
CUDA-backed module, and unsupported shapes/dtypes/GPUs, still need their own cache.
This is a GPU/shape/mode decision, not a blanket family-wide exclusion.

Every Triton kernel retains its global domain in `autotune/configs/grid/`.
`autotune/configs/default/` declares a small initial space per kernel (at most
32 candidates). These are starting configurations, not claims of optimality.
The existing shared-memory predictor, compile-time budgets, shape pruning,
multi-GPU scheduling, resume journals and isolated measurement remain in use.

Valid existing global-search winners can still be used at runtime after checking
their source/toolchain/key identity, global-domain membership and resource prune.
A miss searches only the selected default space; it does not trigger global search.
Explicit custom config directories remain strict: they do not inherit global winners.

```sh
# Production paths, compact Triton spaces, native selectors where implemented.
miniworld-engine build all

# CUDA/CuTe inference tuning over the existing declared inference ladder.
miniworld-engine build all --backend native --mode eval

# Training token lengths are 384 and 768. Atom ladders remain independent.
miniworld-engine build all --mode train

# Opt-in global Triton search, with spare GPUs; forced alternatives are separate.
miniworld-engine build all grid --include-alternatives --gpus all
miniworld-engine build all grid --backend triton --mode eval --gpus all
```

`--mode eval` retains the previous module/driver inference lengths, dimensions,
dtype and augmentation axes. `--mode train` restricts token-pair, token-single and
MSA-token lengths to 384/768. It does not reinterpret atom counts as token lengths.
The inference ladder is not replaced with these two training crops.

`--backend native` means hand CUDA **and CuTe** drivers. `--backend triton` and
`--per-op` explicitly request implementation-level sweeps; they may deliberately
visit alternatives absent from the default production plan. Config breadth
(`default`/`grid`) is independent of backend coverage (`--include-alternatives`).
New policy/mode identities invalidate derived build plans and resume markers;
old measurements remain on disk and are reused only when compatible.

## Are the CUDA kernels already tuned?

Some are, for the shapes/devices in their records. CUDA does not imply a single
fixed configuration, nor does an H100 L384/L768 result cover every inference shape.

| Family | Current tuning mechanism | v2.1 state |
|---|---|---|
| CuTe GEMMs, LNLinear, TriMul components | tile/cluster/persistence candidates, native measured cache | Existing tuner retained |
| CUDA Transition B2B/expand/gate backward | BN, stages, warpgroups, KT, launch bounds | Existing tuner retained |
| CUDA LayerNorm | block/warps/waves/reduction/transaction width | Existing tuner retained |
| Fused Transition D128 | Previously fixed SM-count grid and DW replicas | Added per-GPU/shape forward/backward tuning, candidates validated against retained default |
| Packaged TriMul inference | Width/direction/length tile table, K1/K3 variants | Added exact-shape K1 x K3 selection through the native cache |
| Wide fused Transition, TriMul training checkpoints | Architecture/width-specific schedules and experiment sweeps | Existing schedules retained; not represented as fully globally autotuned |
| TriangleAttention | Shape-specific cell tables and separate tuning tools | Existing selection retained; not a universal native-cache sweep |
| Token DiT | GEMM picker and shape-specific attention schedules | Existing selection retained; FP8 and training paths remain explicit options |
| OPM/PWA and SWA research composites | Packaged or research-specific configurations | No claim of complete inference-space tuning |

The last rows require family-specific extensions and GPU qualification before
claiming a single build command has exhaustively tuned every CUDA component.
Never label a singleton fixed schedule as an exhaustive search.

The new fused selectors retain the previous configuration on a cache miss. A build
validates candidate outputs/saved tensors/gradients against that default before
publishing timings. This comparison does not replace independent correctness,
changed-input graph replay, sanitizer checks or full-module paired timings.

## Why invest in direct CUDA kernels?

For large sustained MiniWorld training/inference workloads, actively consider
GPU-specific fused CUDA implementations, especially for backward. Our pair and
normalization pipelines can spend much of their time writing and rereading large
intermediates. Fusion can remove those transfers; simply enlarging a Triton tile
search cannot change the operator boundaries. The profitable fusion depends on
shared memory, register pressure, occupancy, TMA/WGMMA availability and consumers
of saved activations on the target GPU. Not every operation is memory-bound and
not every additional fusion wins: compare full forward/backward workloads.

With many available GPUs, global Triton searches remain useful for portable
fallbacks and uncovered hardware. Start with the default space and use the global
domain only when the expected deployment savings justify that measurement cost.

## Repository ownership

- `src/miniworld_engine/`: maintained launchers, dispatch and tuning policies.
- `autotune/configs/default/`: small reviewed per-kernel starting spaces.
- `autotune/configs/grid/`: preserved opt-in global spaces.
- `autotune/data/`: measured GPU/shape records; no fabricated re-stamping.
- `tests/`: CPU contracts and explicitly GPU-marked execution checks.
- `experiments/`: research and historical variants, not implicit production APIs.
- `docs/development/`: dated audits; `docs/releases/`: version-specific contracts.

Parent MiniWorld/team-gm pins are updated only to an actual engine commit. Installing
or rebuilding an environment is separate from source/version consolidation.


## CPU validation and release gate

No GPU was requested or used. Slurm jobs used `--gres=none` and `normal_h100`.
The full CPU run (19676) reported 3,967 passed, 16 failed, 279 skipped, with
1,002 GPU tests deselected. Follow-up checks resolved two new policy/registry
failures. The v2.1-focused run (19680) passed 164 tests, with one skip, and
the syntax/undefined-name lint passed. Follow-up registry checks are recorded
in [the validation record](2.1.0-cpu-validation.json).

Thirteen pre-existing failures remain: stale dispatch-derived sweep evidence,
cache identity/MPNN dropout coverage, legacy JIT/compile-wrapper/layout contracts,
and the standalone LayerNorm backend test. The additional v2.1.0 release-manifest
gate also remains red because this version has not run on a GPU. No manifest was
re-stamped and no release tag was created. These are source changes, not a claim
that the complete release suite or new GPU schedules have passed qualification.

The legacy `build trunk`, `build diffusion`, and `build mpnn` targets remain
per-op diagnostic sweeps. Use `build all` or a named module for the production
dispatch policy; explicit per-op/native/Triton sweeps can include fallback paths.
