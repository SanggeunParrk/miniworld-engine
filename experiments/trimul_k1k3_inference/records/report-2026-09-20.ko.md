## 9. 4차 라운드 — SoL 재검토 후 두 가지 채택, 최종 payload 갱신 (`K/payload -> K/var_pdl`)

출발점: "SoL 90%"는 패턴 하한(2.85 TB/s) 기준의 수치였고 HBM peak 기준으로는 K1 73% / K3 77%였다. 남은 여지를 op 단위로 다시 재고, 엔진 경로 op 시간(bench.py)을 기준 지표로 삼았다.

### 9.1 어디에 시간이 남아 있나 (실측)

- **cuBLAS contraction은 교체 대상이 아니다.** NCU(L768): DRAM 읽기 304 MB / 쓰기 139 MB = 필수 바이트(a·b 302 MB 읽기 + X 151 MB 쓰기)와 같음. DRAM 72% + tensor pipe 78%(SM 클럭 1.58 GHz로 전력 스로틀) — 메모리와 연산 한계에 동시에 걸린 균형점. L384는 이미 메모리 하한(DRAM 74%, 113 MB, 39.1 µs). cuBLASLt heuristic 8개 알고리즘을 같은 shape(K = N, batch 128)로 전부 시간 측정: 기본 선택(192×192 nvjet)이 최선(L768 179.1 vs 차선 182.1; L384 44.0 vs 43.9). 이전 보고의 "dense peak 65%"는 스로틀 클럭과 K = N 형태를 무시한 과대평가였다. (`lt_search.cu`, `logs/lt-L*.json`, `logs/ncu-nvjet-L*.ncu-rep`)
- **K1/K3 정상 상태는 이미 스트리밍 하한의 93–95%.** per-CTA 타임스탬프 프로브(`TMN_CTA_TS` 측정 빌드, `ts_probe.py`): 타일당 12.5–12.7K cycle ≈ 7.2–7.4 µs = 144 KB/타일 → 2.65–2.7 TB/s. 남은 손실은 구조적: CTA 시작(launch → 첫 타일 데이터 도착) **K1 4.2–4.4 µs, K3 3.3–4.8 µs**(132 CTA가 동시에 가중치 128/64 KB를 L2에서 끌어오는 fan-out 대역폭), ragged tail(L768: 3072 tile/132 = 23.27 → 96 SM이 마지막 타일 시간 7.4 µs 유휴 ≈ 5.4 µs/커널; L384: 5.82 → 1.3 µs/커널), SM 간 속도 편차(끝 시각 분산 L768 16–18 µs, L384 9–11 µs). NCU per-SM active/elapsed: L384 K1 0.887·K3 0.859, L768 0.925·0.945, nvjet 0.898·0.955.
- **op에 붙어 있던 잡 커널**: 엔진이 넘기는 bf16 pair mask를 face/ops가 매 호출 fp32로 캐스트 — `direct_copy_kernel` **4.4 µs(L384, op의 3%) / 4.9 µs(L768)**. cuBLAS 내부 memset 1.0 µs는 그대로.

### 9.4 SoL 위치 (정직한 판정)

op 복합 하한(3-커널 분해 유지, 패턴 하한 2.85 TB/s, contraction은 실측 균형점 ≈159 µs) ≈ L768 476 µs, L384 ≈ 120 µs → **엔진 op 552.6 µs = 86%, 148.0 µs = 81%**. 남은 14–19%의 구성: 커널 시작 fan-out(K1 4 µs·K3 4 µs; K1 쪽만 PDL로 부분 상쇄), ragged tail(L768 ≈11 µs, L384 ≈3 µs), SM 편차(L768 ≈6 µs), cuBLAS 내부 memset·그래프 간격(≈2–3 µs), contraction 자체의 스로틀 클럭(전력 한계).
미구현 후보(각 ≤2%, 각각 하루 단위 작업): (1) 마지막 wave를 64-token WG 단위로 쪼개는 tail 분할(L768 K1·K3 각 −5 µs, L384 0), (2) 2-CTA cluster TMA multicast로 가중치 fan-out 반감(K3 시작 −2 µs), (3) 엔진의 bool mask 전달(−4 µs, 코드 1줄).
