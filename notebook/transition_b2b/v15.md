## Serialization Analysis

v14 serialized each `BN`-wide `ND` chunk like this:

```c++
consumer_wait(weights[n])
issue expand_a(n)
issue expand_b(n)
warpgroup_wait<0>()
gate(n): a_acc,b_acc -> h_bf
issue squeeze(n)
consumer_release(weights[n])
```

The `warpgroup_wait<0>()` is required before the gate because `a_acc` and `b_acc` are WGMMA outputs. The problem is what happens after that wait: the fp32 SwiGLU gate, including the MUFU work in `sigmoidf_fast`, runs while tensor cores have no useful work from this WG. Since occupancy is smem-capped at one CTA/SM, adding more warps is not available; the remaining lever is to keep a prior or next chunk's WGMMA in flight while the gate runs.

## v15 Schedule

The emitted schedule is a software pipeline over chunks, without double-buffering the large expand accumulators:

```c++
PROLOGUE:
  prefetch_for_chunk(0)
  consumer_wait(0)
  issue expand(0): commit expand_a(0), commit expand_b(0)

LOOP chunk n:
  if n == 0:
    warpgroup_wait<0>()        // no previous squeeze exists yet
  else:
    warpgroup_wait<1>()        // leaves squeeze(n-1) in flight

  gate(n): a_acc,b_acc -> h_bf[n & 1]

  if n + 1 < kNumChunks:
    consumer_wait(n+1)
    issue expand(n+1): commit expand_a(n+1), commit expand_b(n+1)

  issue squeeze(n): commit squeeze(n)
  consumer_release(n)
  prefetch future weights for chunk n+1, if any

EPILOGUE:
  warpgroup_wait<0>()
  existing vectorized output shuffle/store epilogue
```

TMA prefetch for the future ring slot is deliberately placed after `consumer_release(n)`. In the original loop the future prefetch happened at the top of the next iteration, after the previous stage was already released. In this pipelined loop, doing that prefetch before release could reacquire the current stage when the ring wraps. The current chunk's next-stage weights are already resident from the earlier ring prefetches, so `consumer_wait(n+1)` can still happen before `squeeze(n)`.

## WGMMA Commit-Group Accounting

Each chunk contributes three WGMMA commit groups:

- `expand_a(n)`: one commit group writing `a_acc`
- `expand_b(n)`: one commit group writing `b_acc`
- `squeeze(n)`: one commit group accumulating into persistent `out_acc`

After the prologue for chunk `0`, the pending queue is:

```text
[expand_a(0), expand_b(0)]
```

There is no previous squeeze to preserve, so the first loop iteration uses `warpgroup_wait<0>()` before reading `a_acc` and `b_acc`.

In the first steady iteration, the previous iteration issued the next expand before the current squeeze:

```text
[expand_a(n), expand_b(n), squeeze(n-1)]
```

`warpgroup_wait<1>()` drains the two oldest commit groups, `expand_a(n)` and `expand_b(n)`, leaving exactly one younger group, `squeeze(n-1)`, outstanding. That makes `a_acc` and `b_acc` safe for `gate(n)` while keeping tensor-core work in flight during the gate.

After the pipeline is fully warm, there can also be an older squeeze at the head of the queue:

```text
[squeeze(n-2), expand_a(n), expand_b(n), squeeze(n-1)]
```

The same `warpgroup_wait<1>()` is still the correct depth: it drains `squeeze(n-2)` plus the two expand groups for chunk `n`, and leaves only `squeeze(n-1)` in flight for overlap with `gate(n)`.

After `gate(n)` consumes `a_acc` and `b_acc`, v15 reuses the same accumulator objects for `expand(n+1)`. The live pending queue then becomes:

```text
[squeeze(n-1), expand_a(n+1), expand_b(n+1)]
```

Then `squeeze(n)` is issued, so the next iteration starts with:

```text
[squeeze(n-1), expand_a(n+1), expand_b(n+1), squeeze(n)]
```

The next `warpgroup_wait<1>()` drains through `expand_b(n+1)`, leaving `squeeze(n)` as the single in-flight group. This is the intended overlap: gate(n+1) hides under squeeze(n), and squeeze(n) has already been placed after expand(n+1) so it can overlap the next expand issue window.

`warpgroup_fence_operand(a_acc)` and `warpgroup_fence_operand(b_acc)` are kept before WGMMA writes and before gate reads. `warpgroup_fence_operand(out_acc)` remains before the loop and after the final drain.

## Accumulator Reuse

v15 does not double-buffer `a_acc` or `b_acc`. The correctness argument is:

1. `warpgroup_wait<0>()` or steady-state `warpgroup_wait<1>()` guarantees `expand(n)` is complete before the gate.
2. `gate(n)` reads every element of `a_acc` and `b_acc` and writes the bf16 squeeze operand.
3. Only after that consume step does v15 clear and reuse the same `a_acc` and `b_acc` objects for `expand(n+1)`.

This avoids adding another two large fp32 accumulator fragments, which would almost certainly exceed the already tight v14 `255` register budget.

## h Buffering Choice

Chosen path: option (i), double-buffer only the bf16 `h` / RS-A operand registers.

The loop allocates `h_bf0` and `h_bf1` and selects `h_bf[n & 1]`. This protects `squeeze(n)` from `gate(n+1)` overwriting the same bf16 operand while `squeeze(n)` is still the single outstanding WGMMA group. The large `a_acc` and `b_acc` fragments remain single-buffered.

To offset some register pressure, v15 no longer materializes a full fp32 `h_acc` fragment. It computes the same fp32 expression per element and casts directly to the selected bf16 `h_bf` fragment:

```c++
const float h = a * sigmoidf_fast(a) * b;
h_bf(i) = static_cast<BF>(h);
```

This keeps the math order and precision of the gate expression while avoiding a full additional fp32 temporary fragment. ptxas must still confirm whether the second bf16 `h` buffer causes any stack or local-memory spill.

Specific correctness risks to watch:

- Accumulator reuse ordering: `a_acc` and `b_acc` are reused for `expand(n+1)` only after `gate(n)` consumes them. A cosine failure can indicate that `warpgroup_wait<1>()` did not leave the intended younger group or that a compiler/scheduling change moved a read across the reuse boundary.
- h lifetime: `h_bf0/h_bf1` must be sufficient because only one prior squeeze is intentionally left in flight at each gate. If more than one squeeze remains pending, ping-pong `h` is not enough.
- TMA stage lifetime: v15 waits chunk `n+1` before releasing chunk `n`, but it delays future prefetch until after release to avoid reacquiring the current ring slot too early.
- `out_acc` accumulation order: squeeze commit order remains chunk order `0..kNumChunks-1`, and the final `warpgroup_wait<0>()` still drains before the vectorized store epilogue.

## Validation + results (H100) — ❌ REGRESSED (spill), reverted to v14
- cos(cuda,triton) = 1.000000 (correct). Perf (M=524288): v15 = **620.7-635.7 us = 0.85-0.87x** of
  Triton — a large REGRESSION vs v14 (~421us/1.29x).
- **ptxas: `REG:255 STACK:224 LOCAL:0`** — the kernel SPILLED (224 B stack). The software-pipeline's
  extra live state (double-buffered `h` + the two expand accumulators live across the reordered
  issue/gate/squeeze window) pushed past the 255-reg / 1-CTA budget, forcing spill. The spill traffic
  far outweighs any wgmma-overlap benefit.
- Verdict: REGRESSED — reverted to v14. This was the anticipated risk: at 1 CTA/SM / 255 regs there is
  no register headroom to software-pipeline the ND loop, even with only `h` double-buffered and the
  fp32 `h_acc` fragment removed. The `wait 1.34` stall is therefore a genuine occupancy-bound floor for
  this structure — it cannot be hidden without more registers (which need higher occupancy, which is
  smem-blocked). **v14 = ~421us = 1.29x is the practical hand-CUDA ceiling for the fused b2b at d=128.**
