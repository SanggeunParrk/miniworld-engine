# triangle_multiplication_tm1_cute - optimization round v4

- Date: 2026-07-03
- Target kernel: `triangle_multiplication_tm1_cute` (from-scratch SM100 track, cont. of v3)
- Baseline version: v1 (perf), v2 (current best fused-gate)

## 1. Goal
Continue the from-scratch SM100 tcgen05 GEMM. v3 got it to COMPILE but it deadlocked at
launch; v3 hypothesised the `mbar_acc` / `tcgen05.commit` accumulator handshake. This round
BISECTS the deadlock to find the true cause before attempting a fix.

## 2. Method: launch-hang bisection (CUDA_LAUNCH_BLOCKING=1, torch reference M=256,N=K=128)
All variants compile in ~0.3s; the question is only whether the kernel launch completes.

| variant | change vs full kernel | result |
|---------|-----------------------|--------|
| bisect  | MMA block removed (TMA load + TMEM alloc + epilogue store only) | **COMPLETES** (no hang) |
| bisect2 | MMA + `tcgen05.commit` kept, `mbar_acc` wait dropped | HANGS at launch |
| bisect3 | MMA `cute.gemm` loop only, no commit, no wait | **HANGS at launch** |
| full+fix| `cute.gemm` moved inside `elect_one` (single-thread issue) | HANGS at launch |

## 3. Conclusion (corrects the v3 hypothesis)
- The deadlock is **the tcgen05 UMMA issue itself** (`cute.gemm` on the SM100 tiled_mma),
  NOT the `mbar_acc`/commit handshake and NOT the mbarrier wait (v3's guess was wrong).
- Evidence: bisect3 has no commit and no wait, yet still wedges the device; bisect (identical
  except the `cute.gemm` loop is absent) completes cleanly. So the TMA-load, TMEM
  allocate/retrieve, TMEM->reg->smem->gmem epilogue, and per-epi-subtile TMA store paths are
  all correct and functional. Only the MMA wedges.
- Moving `cute.gemm` inside `elect_one` (single-thread UMMA issue, which is more correct than
  the warp-level issue) did not change the outcome -> the issue is in the MMA operand setup,
  not the number of issuing threads.

## 4. Remaining blocker (genuine, unresolved after real effort)
The UMMA never retires / the device spins. Most likely the A/B **smem descriptors** or the
**TMEM accumulator layout** handed to `cute.gemm` are subtly wrong for a tcgen05 SS-mode MMA,
so the MMA hardware stalls. Candidates for the next session:
1. A/B fragments: I build `tCrA = tiled_mma.make_fragment_A(sA0)` from a *stage-sliced* 3-mode
   smem tensor; quack builds it from the *full 4-mode staged* smem and indexes `[None,None,k,stage]`.
   Try keeping the staged smem tensor and indexing the stage, matching quack exactly.
2. MMA instruction shape: `make_trivial_tiled_mma(..., (128,128))` -> verify the 128x128x16
   UMMA atom is legal for CtaGroup.ONE and that `partition_shape_C`/`make_fragment_C` produce
   the tmem layout the atom actually writes.
3. Possible missing `tcgen05` fence / tmem-accumulator "reset" before the first MMA, or a
   required `cute.arch.fence_view_async_tmem_store()` ordering around the UMMA.
4. Fastest unblock: adopt `cutlass.pipeline.PipelineUmmaAsync` + `PipelineTmaUmma` for the AB
   and accumulator stages instead of bare mbarriers, i.e. converge toward quack's structure
   (the only known-good SM100 reference in this env), then reintroduce the single-CTA
   simplifications.
