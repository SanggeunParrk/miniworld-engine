# trimul_bidir_b200 v5 — wire the module to the v6-faithful bidir kernel

**Type:** integration / wiring fix (no kernel change). **GPU:** NVIDIA B200 (sm_100), bf16, B=1.

## Problem

`BidirectionalTriangleMultiplication._forward_cute_train` (the MINIWORLD training path) imported
`BidirTriMulB200Train` from `bidir_training_b200.py` — the **v2** bidir kernel built on the v9
save-heavy sm100 stack (per-direction tcgen05 gated fronts + 8 `_fast_T` transposes/iter). The
docstring *claimed* "trimul_bidir_b200 v4", but v3/v4 had actually landed a separate, faster
kernel — `BidirV6TriMulSm100` in `bidir_training_sm100.py` (the v6-faithful design: m-major front
0 transposes, `_te_forward/_te_backward`, fused gate, `bmm(out=...)` slices instead of `torch.cat`)
— which **nothing imported**. So the module silently ran the slow v2 kernel.

Measured consequence (single fused bidirectional trimul TRAINING, cudagraph, gseed loss):

| L | v2 (wired) | cuequiv | v2 vs cuequiv | 2×single-dir v6 |
|---|---|---|---|---|
| 384  | 1.464 | 2.264 | 1.55× | 1.181 |
| 512  | 2.248 | 3.739 | 1.66× | 1.885 |
| 1024 | 8.224 | 13.75 | 1.67× | 6.788 |

The fused bidir was **slower than just running two single-direction v6 kernels** (8.224 vs 6.788 ms
@L1024) — it should be *faster* (shared LN_in + shared final gate). This dragged the pairformer
`trimul_only` composite down to ~1.3× vs cuequiv.

## Fix

Repoint `_forward_cute_train` to the existing v6-faithful kernel, mirroring the single-direction
module's arch dispatch: sm_100 → `BidirV6TriMulSm100`, else sm90 → `BidirV6TriMul`. The duplicate
rewrite attempted in `bidir_training_b200.py` this round was reverted — the shipped v4 kernel is
strictly better (its `bmm(out=tri[:h])` slices avoid the `torch.cat` my rewrite used).

## Validation (correctness)

`BidirV6TriMulSm100` vs the pytorch reference (`BidirectionalTriangleMultiplication`, dense, L=256,
bf16, **randomized weights** — the module zero-inits to_out/to_gate/gates, which gives cos 0/0):

| fwd | d_pair | dWL | dWp | dWg | dLN_in | dLN_out |
|---|---|---|---|---|---|---|
| 0.999983 | 0.999972 | 0.999999 | 0.999999 | 0.999961 | 0.999999 | 0.999999 |

## Performance (after fix)

Fused bidirectional trimul TRAINING (cudagraph, bf16, gseed loss):

| L | v6-faithful (now) | cuequiv | **vs cuequiv** | 2×single-dir | vs 2×single |
|---|---|---|---|---|---|
| 384  | 0.889 | 2.264 | **2.55×** | 1.179 | 1.33× |
| 512  | 1.458 | 3.742 | **2.57×** | 1.885 | 1.29× |
| 1024 | 5.537 | 13.75 | **2.48×** | 6.788 | 1.23× |

Bidir training goes from **1.67× → ~2.5× vs cuequiv** (kernel 1.48–1.65× faster: 8.224→5.537 ms
@L1024) and now correctly beats two single-direction v6 calls (shared LN_in/gate). Restores the
~2× trimul advantage in the bidirectional formulation.

### End-to-end pairformer `trimul_only` (bidir trimul + transition, n_block=4, TRAINING):

| L | ours vs cuequiv (before) | ours vs cuequiv (after) |
|---|---|---|
| 256 | 1.35× | **1.78×** |
| 384 | 1.32× | **1.73×** |
| 512 | 1.38× | **1.72×** |

(ours L=512 training 16.03 → 12.85 ms.) Inference `trimul_only` is unchanged (1.30–1.37×) — it
uses the forward-only cute path, not the training kernel, so it was never mis-wired. The composite
stays below the standalone bidir 2.5× because the block also runs `transition`, which has no
cuequiv kernel (both sides fall back to the same triton/pytorch path → parity, pure dilution).
