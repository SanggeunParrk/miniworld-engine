# trimul_train_b200 v14 — fuse the front GLU into the GEMM epilogue

**Target:** the sm100 (B200) trimul TRAINING front (`front_train_sm100.trimul_front_sm100_train`),
used by `V6TriMulMergedSm100` (single-dir) and the bidir front (same parameterized function).

**Base:** v13 (`541c680`), front = quack non-gated m-major GEMM `x@b_lr -> preact[4D,L,L]` +
Triton `_glu_bdll_kernel` that RE-READS preact[4D] to emit `left/right[2D,L,L]`.

## 1. Profiling (before)

Front isolated (CUDA-graph do_bench, L=1024, D=128, B=1):

| stage | L=384 | L=768 | L=1024 |
|-------|-------|-------|--------|
| GEMM (preact write)      | 38.8us | 141us | 265us |
| `_glu_bdll` (preact re-read + lr write) | 42.9us | 139us | 238us |
| full front              | 74.8us | 274us | 495us |

Key finding: **the GLU is ~as expensive as the GEMM** (not cheap!). It is HBM-bandwidth-bound
re-reading `preact[4D]` (~1.07 GB @ L=1024) + writing `lr[2D]` (~0.54 GB) = 1.62 GB at ~6.7 TB/s
(near the B200 HBM ceiling). The GEMM itself is ~bandwidth-bound writing preact (1.08 GB). Total
front HBM traffic (2-launch) = write preact (1.08) + read preact (1.07) + write lr (0.54) = **2.7 GB**.

## 2. Hypothesis

Fuse the GLU into the GEMM epilogue: emit BOTH `left/right[2D]` (GLU) AND `preact[4D]` (raw logits,
still needed by backward `front_bwd_dW`, which is UNCHANGED) directly from the in-TMEM accumulators.
Traffic drops to write preact (1.08) + write lr (0.54) = **1.62 GB** (kills the 1.07 GB preact
re-read + the second launch).

## 3. Implementation

`front_fused_gemm_sm100.FusedPreactGemmKernel` subclasses the WORKING inference
`GatedPersistentGemmKernel` (tm1.cute.sm100_gate_gemm_collective): dual-B (Bp/Bg share one A load),
two tcgen05 MMAs -> proj[2D] + gate[2D] TMEM accumulators, TMA-store epilogue. The subclass ADDS
two TMA stores in the epilogue so the raw pre-GLU logits are also written, in the exact interleaved
`[g,p]`-per-plane `(4D,M)` M-major layout backward consumes:

```
gate[d] (d=0..2D-1, left|right) -> preact even planes preact.view(4D,M)[0::2]   (strided TMA, N-stride 2M)
proj[d]                          -> preact odd  planes preact.view(4D,M)[1::2]   (strided TMA)
sigmoid(gate[d])*proj[d]         -> lr[2D,M] contiguous (left = lr[:D], right = lr[D:])
```

Bp/Bg = the proj / gate columns of the interleaved `b_lr`: `Bg = b_lr[:,0::2].T`, `Bp = b_lr[:,1::2].T`.

Two implementation problems had to be solved (each cost a ~2-4x regression until fixed):

1. **Store serialization.** The naive 3-stores-with-a-barrier-pair-each epilogue was ~4x slower
   (254us -> 1036us). Fixed by filling 3 smem buffers, then ONE fence + ONE barrier pair, then
   issuing 3 overlapping TMA stores.
2. **smem allocation.** The parent maxes the AB (load<->MMA) pipeline — pointless here (K=D=128 is a
   SINGLE k-tile) and it starved `num_c_stage` to <3, which both serialized and *aliased* the 3
   per-subtile store buffers (silent corruption at large L). `_setup_attributes` override: shallow
   AB (2 stages), MAX C stages (=16) -> a deep TMA store pipeline that streams at HBM bandwidth.
3. **[decisive] sigmoid.** The IEEE-divide "exact" sigmoid costs **~0.32 ms** of pure division over
   `2D*M` elements (documented in the inference collective). Switching to the division-free
   `1/d == rsqrt(d)^2` form (rsqrt -> fast MUFU) took the whole fused front from 845us -> 258us for
   the 1-store case (matching inference), and the full 3-store front to 393us. rsqrt is bit-accurate
   enough (see gate).

Precision unchanged: bf16 in / fp32 acc / bf16 out; preact stores the raw bf16 logits (backward
re-applies sigmoid, as before). Algorithm identical — fusion only.

## 5. Performance (training graph replay, single-dir, D=128, B=1, bf16)

| L | v13 graph | v14 graph | v14 vs v13 | cuequiv | v14 vs cueq |
|---|-----------|-----------|-----------|---------|-------------|
| 384  | 0.653 ms  | 0.634 ms | **1.03x** | 1.108 ms | 1.75x |
| 768  | 2.2205 ms | 2.178 ms | **1.020x** | 3.963 ms | 1.82x |
| 1024 | 4.0527 ms | 3.887 ms | **1.043x** | 6.998 ms | 1.80x |

(L=384 back-to-back on/off, 2 reps each: fused 0.627/0.642 vs v13 0.654/0.651 — the single-run
0.641 above was the high side of noise; v14 is a consistent small win at every L, no regression.)

Front-isolated speedup (CUDA-graph do_bench): 384 1.13x, 768 1.16x, **1024 1.24x** (495->397us).
The graph-level win is smaller because the front is ~12% of the graph; the fusion removes the
preact re-read, which grows with L (hence the win grows with L).

## 6. Remaining headroom / next ideas

- The fused epilogue does 3 M-major TMA stores through one shared smem staging; the preact planes
  are STRIDED (N-stride 2M). A contiguous preact store (single-MMA N=4D + in-epilogue N-halving GLU)
  could store preact more efficiently but requires adjacent-column (gate/proj) thread co-location —
  the exact hazard that broke the StMatrix m-major store (front header). Not attempted.
- The `Bp/Bg = b_lr[:,::2].t().contiguous()` derivation is 2 small copies per forward; could be built
  directly from the weights (or in prepack) to shave the small-L overhead.
- The front GEMM is still tensor-underutilized (K=128 single k-tile); split-K was not pursued because
  the front is now bandwidth-bound on the 1.62 GB of stores, not MMA-bound.
