# trimul_train_b200 v15 — front GEMM config search (NEGATIVE)

**Target:** the v14 fused front GEMM (`FusedPreactGemmKernel`). Base: v14 (`6fa52df`).

## Motivation

After v14 the front is: base GEMM+lr store (== inference `gate_gemm`, ~255us @ L=1024) + two
extra preact TMA stores (~139us for +1.08 GB = ~7.7 TB/s, near the HBM ceiling). The 2 preact
stores are already near peak bandwidth, so the only remaining lever is the **base GEMM** (255us),
which ncu (v12) showed is tensor-underutilized (25%) / low-occupancy (11%) because K=D=128 is a
SINGLE k-tile that starves the MMA pipeline. Hypotheses: a 2-CTA cluster (better MMA + TMA-multicast
of the shared A) or a different tile/stage config could raise MMA utilization.

## Experiments (fused front, CUDA-graph do_bench, L=1024, D=128)

| config | fused front |
|--------|-------------|
| **v14 default: tile(128,128) cluster(1,1) ab=2** | **394 us** |
| tile(128,128) cluster(2,1) use_2cta | 536 us (regress) |
| tile(128,128) cluster(1,1) ab=3 | 428 us (regress) |
| tile(128,64)  cluster(1,1) ab=1 | 692 us (regress) |
| tile_m=256 / tile_n=256 | compile error (tcgen05 M-mode must be 64/128) |

## Result: NEGATIVE

No config beats the v14 default. The 2-CTA cluster regresses ~1.36x (the dual-accumulator +
2-CTA epilogue partition/dealloc overhead outweighs any MMA/multicast benefit at this shape).
Smaller tiles multiply the tile count (more epilogue passes). `tile_m` is hardware-capped at 128
for the bf16 tcgen05 MMA.

The base GEMM's low MMA utilization is inherent to the single-k-tile (K=128) shape; but the fused
front is now **store-bound** (1.62 GB) rather than MMA-bound, so raising MMA utilization would not
move the wall-clock. split-K (v-hypothesis 2) was not pursued for the same reason: it targets MMA
starvation, which is not the binding constraint after fusion.

Conclusion: the v14 fused front is at its practical ceiling. No code change committed (config knobs
were experimental only; the shipped kernel keeps the v14 default). Front optimization converged.
