# te_style LN backward on B200 (sm_100) — v2: maxnreg-capped autotune (occupancy)

Round 2 on the te_style fused `_ln_bwd_kernel` (the LN_out backward: `dx` + `dγ` + `dβ`,
m-major in→out, atomic M-reduction). v1 shipped the "uniform m-major layout" win (1.33–1.45×)
and left the kernel **register-pressure / occupancy-bound** as the open wall. This round attacks
that wall directly.

## Environment
- B200 (sm_100, cap 10.0), driver 580.95.05, torch 2.10.0+cu128 (nvcc 12.8), triton 3.x, bf16,
  B=1, D=128 (N=128), M=L² for L∈{384,768,1024}.
- Repo `~/psk/miniworld-engine` @ 8785f24 (shipped main). Run:
  `pixi env python … QUACK_CACHE_ENABLED=0`, `CUDA_VISIBLE_DEVICES=<idle>`.
- Standalone harness: `~/psk/ncu/exp_maxnreg.py` (uniform m-major inputs = shipped `_te_backward`
  layout, do_bench warmup=25/rep=100 median). Gates: `~/psk/ncu/{verify_v12,graph_train_v12}.py`.

## Profile (baseline, this GPU/session)
`_ln_bwd_kernel` winning autotune config @ L=768/1024 = **BLOCK_M=64, num_warps=4, maxnreg=None**.
From v1 ncu: 255 regs/thread → **2 resident blocks/SM** → ~12% warp occupancy; DRAM ~15–26%
(NOT bandwidth-bound). Fresh full-step ncu (v14_nodegap): 489 µs, SM 39% / DRAM 26% / occ 24% —
**latency/occupancy-bound**, neither compute nor memory saturated.

## Bottleneck theory
Latency-bound with too few resident warps to hide the `load → row-reduce(c1,c2) → dx` dependency
chain (+ atomic dγ/dβ). Occupancy is capped by registers: 255 regs → 2 blocks/SM. The v1 data
point that the *contiguous* LN_in case runs at **167 regs → 3 blocks/SM** shows a 3rd block is
reachable if the m-major kernel's register footprint is forced down.

Key gap: **every config in `_LN_CONFIGS` had `maxnreg=None`** — the autotuner never got to trade a
few register spills for the 3rd resident block. BLOCK_M∈{8..128} was swept, but the tuner picked
BLOCK_M=64 (255 regs); smaller BLOCK_M lost on work-per-block, so occupancy was never recovered.

## Experiment
Add `maxnreg`-capped variants to the shared `_LN_CONFIGS` (`BLOCK_M∈{32,64,128}`, `num_warps=4`,
`num_stages∈{2,4}`, `maxnreg∈{128,168}`; +12 configs → 57). Hypothesis: `maxnreg≈168` lets
BLOCK_M=64 reach 3 blocks/SM, raising occupancy and hiding latency. Expected +5–10% on the
kernel. Precision-neutral (register **allocation** only — math unchanged). Risk: spill traffic
outweighs the occupancy gain → autotuner just keeps `None` (no regression, only autotune cost).

## Result (standalone `_ln_bwd`, uniform m-major, same GPU/script before→after)
| L | M | baseline (maxnreg=None) | +maxnreg | speedup | winning cap |
|---|---|---|---|---|---|
| 384 | 147456 | 0.0524 ms | 0.0524 ms | 1.00× | (None; BLOCK_M=32) |
| 768 | 589824 | 0.1774 ms | 0.1690 ms | **1.05×** | maxnreg=168, BLOCK_M=64 |
| 1024 | 1048576 | 0.3042 ms | 0.2837 ms | **1.07×** | maxnreg=168, BLOCK_M=64 |

Confirmed the theory: the win appears exactly where the register wall bit (large M, BLOCK_M=64);
small L (BLOCK_M=32, already <255 regs) is unaffected. dx/dγ/dβ cos **0.999999** (unchanged).

## Validation (CUDA-graph, fwd+bwd, full V6TriMulMergedSm100)
- `verify_v12`: grads vs fp32 ref, worst grad cos **0.999982** @ L=384/768/1024 (identical to
  baseline — register-allocation change does not move values). PASS @0.9999.
- `graph_train_v12`: graph-replay grads vs eager, worst_cos **1.000000** at all L (no kernel
  dropped from capture → graph valid). PASS.

## End-to-end note (honest)
LN_out-bwd `_ln_bwd_kernel` is ~9% of the training step, so a 7% kernel win ≈ **~0.6% of the
step** — below graph-time run-to-run noise on an unlocked-clock GPU (observed absolute graph-time
wandered ~2× between sessions). No e2e speedup is claimed; the defensible result is the
same-condition standalone kernel measurement above. The change strictly *adds* autotune options
(autotuner keeps `None` where it doesn't win), so it can only help or tie — landed on that basis.

## Next ideas
- Kernel fission (dx-only kernel + a dedicated dγ/dβ column-reduction) to remove atomics from the
  hot path — but v1 showed the partial/persistent reduction variants are *slower* (scratch
  [M,N] round-trip), so low odds.
- The real remaining ceiling is the m-major strided access + 3-block/SM occupancy; further gains
  likely need a from-scratch CUDA kernel (the contiguous `_bwd_cuda_impl` is faster but only for
  the LN_in contiguous layout, not this m-major one).
