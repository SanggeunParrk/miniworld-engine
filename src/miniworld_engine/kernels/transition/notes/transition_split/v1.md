# transition split (d=512) — v1: baseline ncu analysis

Branch `b2b-cutlass-opt`. Target: the **d=512 "split" forward** = cute expand+gate GEMM
(`transition_expand_swiglu_cute`, quack GemmLnGatedSm90 WGMMA) → h[M,ND], then cuBLAS
squeeze `torch.matmul(h, Ws^T)`. b2b fusion is ruled out at d=512 (smem can't co-hold
xn+weights+accumulator; see transition_b2b/highdim-and-split.md). This round is
**analysis only** — no code change.

## Bottleneck theory — expand (533.9 us)
- **Compute/tensor-bound but occupancy-starved.** SM 69.8%, SM-busy 70.4%; the highest-
  utilized pipe is Shared/Tensor(FP) at 70.4% (tensor sub-pipe dominant). DRAM only 21.5%,
  L2 hit 90% -> NOT memory-bound.
- **Occupancy co-limited to 1 CTA/SM by BOTH resources:** Block Limit Registers = 1
  (168 reg/thread x 384 thr ~= 64.5K ~= the 64K/SM cap) AND Block Limit Shared Mem = 1
  (220 KB/block of ~228 KB usable). Theoretical occ 18.75% (12 warps/SM = 3 warps/sched),
  achieved 14.0% (8.97 warps/SM).
- **Scheduler starved:** avg 2.24 active warps/scheduler, eligible 0.35/sched, "No
  Eligible" 70.8%, issued IPC 1.17 (of 4). Warps stall waiting on WGMMA/TMA/barriers with
  too few peers to hide it. This is the classic pingpong-WGMMA low-occupancy point.
- Config in use (K>=256 branch): **tile_m=192, tile_n=128, pingpong=True, cluster(1,2)**.
  ncu "Est. Speedup" if occupancy raised ~= 27%.

Ceiling: if expand could reach the squeeze's ~87% tensor utilization, 534 -> ~430 us
(-20%), cutting split ~759 -> ~655 us (M=65536). Whether that's reachable depends on
whether the pingpong tile is already at its design point.

## Plan for v2 (proposed, not yet run)
**GemmConfig sweep at d=512** — data-driven, low-risk, no kernel rewrite:
- tile_m in {128, 192, 256}; tile_n in {64, 128} (gated needs %32; pingpong caps n<=128).
- pingpong in {True, False}; cluster in {(1,2),(2,1),(2,2),(1,4)}; max_swizzle in {4,8}.
- Hypothesis A: smaller tile_n (64) halves smem/stage -> allows 2 CTAs/SM or more mainloop
  stages -> more eligible warps -> fill idle issue slots. Risk: smaller tiles cut tensor
  efficiency (opposing force). Hypothesis B: larger cluster improves TMA multicast / L2
  reuse of the shared xn operand.
- Measure per-config: kernel us + SM% + achieved occ; keep the cos>=0.99999 check.

## Next ideas (if sweep plateaus)
- Explicit mainloop STAGES bump if any smem is freed by a smaller tile.
- Revisit whether the LN-fold epilogue (extra C1/B2/S loads + register-permute gate) is
  inflating the 168-reg / 220-KB budget vs a plain gated GEMM; if so, trim the epilogue.
