# triangle_attention `_attn_bwd` — v2: FA2-style two-kernel split (SHIP, 1.31×)

**GPU:** H100 (sm90).  **Shape:** d_pair=512, L=384, n_head=4 → HEAD_DIM=128, B=1, bf16.
**Kernel:** `src/miniworld_engine/kernels/triangle_attention/triton/main.py`
**Baseline for this round:** the contiguous single-kernel `_attn_bwd` (b2ce813).

## Verdict

**SHIP.** Splitting the fused `dq+dk+dv+dbias` backward into two FA2-style kernels
(`_attn_bwd_dkdv` + `_attn_bwd_dq`, register-accumulated dq, no atomics) is correct
(cos 0.99999 / 0.99998 vs pytorch fp32 ref) and gives **fwd+bwd step 10.98 → 8.36 ms/layer
(1.31×)**; the attention backward itself drops **~4.44 → ~2.13 ms (~2.1×)**.

## Bottleneck theory (carried from v1 + this round's ncu)

v1 proved the fused kernel was register-walled (255 reg → 12.5 % occ) and **dominated by
`long_scoreboard` (8.55 cyc/issue) = global-load-latency**, and that no tile/warp/stage
tuning moved occupancy. v2's ncu shows the split does **NOT** raise occupancy (dkdv still
244 reg / 12.4 %, dq 224 reg / 6.2 %) — yet it is 2× faster. So the real limiter was never
occupancy; it was the **memory access pattern** of the fused kernel:

- `long_scoreboard` 8.55 → **2.5 (dkdv) / 2.2 (dq)**
- SM throughput 9 % → **28.6 % (dkdv) / 20.6 % (dq)**

Two causes removed by the split:
1. **atomic_add(dq)** every inner iteration (RMW global traffic + serialization) — gone;
   dq is now a register accumulator stored once.
2. **redundant q/dO loads.** The fused kernel fixes a KV block and reloads q/dO for every
   query row on every one of the L/BLOCK_N n-blocks. The new `_attn_bwd_dq` fixes a query
   block and loads q/dO **once**, then streams K/V — far fewer redundant global loads.

## Plan (this round)

Split the fused backward into the canonical FA2 pair:
- `_attn_bwd_dkdv`: fix a BLOCK_N key/value block, loop query rows, accumulate dk/dv,
  store dbias(=dS). Byte-for-byte the old kernel minus the dq atomic path.
- `_attn_bwd_dq`: fix a BLOCK_M query block, loop K/V blocks, recompute P/dS, accumulate
  dq in registers, store once. No atomics.
- Keep dbias per-row store + `reduce(sum)` and the merged (H·L) batch layout unchanged.
- `dq = torch.empty_like` (no zero-init; fully written) — drop `reset_to_zero`.

Precision unchanged (fp32 accumulators, bf16 storage).

## Regressions / risks

None observed. dq is now fp32 `empty` (was `zeros`) — safe because `_attn_bwd_dq` writes
every element it owns. Correctness re-verified.

## Next ideas (v3+)

- **stride-native loads** to remove the `.contiguous()` copies (now the largest single
  slice at ~24.6 % of the shrunken step). Must be done in the kernel load path (not by
  dropping `.contiguous()` blindly — that regressed in an earlier experiment via gappy
  loads). Potential ~2 ms.
- Fuse the dbias `reduce(sum)` into `_attn_bwd_dkdv` (atomic or block-reduce over the row
  dim) to drop the per-row 452 MB `dbias` intermediate.
- Tune BLOCK_M/BLOCK_N separately per split kernel (dq now has a different footprint).
